# Как выпускаются готовые сборки

Git хранит исходники и историю их изменений. GitHub Releases хранит готовые
файлы, привязанные к выбранному тегу (именованной отметке коммита).
Так человек может либо скачать установщик, либо получить ровно те исходники,
из которых он собирался. `.deb` не нужно коммитить в историю.

## Что получает читатель

На странице выпуска:

- `cpp-backend-course-desktop_ВЕРСИЯ_amd64.deb` — приложение Linux x86-64;
- `cpp-backend-course-web_ВЕРСИЯ.zip` — готовый веб-сайт;
- `cpp-backend-course-local_ВЕРСИЯ.zip` — автономный браузерный курс;
- `SHA256SUMS` — контрольные суммы этих трёх файлов.

Архивы **Source code**, которые GitHub добавляет сам, — исходники по тегу,
а не ещё одна готовая локальная сборка. Для работы с ними нужны команды
из [BUILDING.md](BUILDING.md).

Контрольная сумма проверяет совпадение байтов с опубликованным списком.
Она не является подписью автора и не защищает от одновременной подмены
самого файла и списка сумм.

## Подготовить выпуск

1. Измени версию в `desktop-course/app/package.json`, если выпускается новая версия.
2. Обнови материалы и пересобери нужные страницы из их исходников.
3. Выполни `python3 tools/course.py check`, проверь существенные изменения
   в браузере и ознакомься с ограничениями тестов.
4. Закоммить и отправь изменения обычным push. Не перезаписывай старый тег.
5. Создай тег, совпадающий с версией приложения. Например, для 1.1.1:

```sh
git tag -a desktop-v1.1.1 -m "C++ Backend 1.1.1"
git push origin desktop-v1.1.1
```

Эта отдельная отправка тега запускает `Course release` из
`.github/workflows/release-desktop.yml`. Указывать здесь нужно уже проверенный
коммит, а не создавать тег до завершения работы.

Workflow также можно запускать вручную через Actions, если выбранный тег
и версия удовлетворяют его проверкам. Точные поля показаны в форме запуска.
Для такого запуска workflow должен быть в основной ветке; нужны права записи.

## Что делает автоматизация

Сборка проходит на Ubuntu 24.04: проверяет исходники и полную полученную историю
на секреты, собирает обе браузерные раздачи, получает закреплённый Electron
и создаёт `.deb`. Проверка самого детектора на вымышленных данных также обязательна.
Готовые файлы вместе
с контрольными суммами передаются заданию публикации.

Только задание публикации получает `contents: write`. Оно создаёт черновик
Release, загружает проверенные вложения и делает выпуск публичным после
проверки результата. Существующие выпуски и их файлы не заменяются молча.
Личные токены не нужны; используется временный токен этого задания.

Успешная сборка не означает автоматическую проверку всех C++-примеров,
настоящих серверных стендов и каждого окна приложения. В описании выпуска
нельзя приписывать сборщику такие проверки.

Если выпуск остановился, сначала прочитай ошибку в Actions. Не исправляй
проблему отключением песочницы, публикацией личного токена или принудительной
заменой уже используемого тега. Неудачный черновик нужно проверить отдельно:
из-за него повторная публикация той же версии может быть намеренно запрещена.

## Почему не хранить .deb в Git

Установщик содержит готовый движок и занимает около 97 МБ. Он не нужен человеку,
который меняет текст курса или читает исходники. Старые бинарники сохранялись
бы в истории и утяжеляли клонирование. Releases отделяет установщики от исходников.
GitHub также [рекомендует Releases для больших бинарных файлов](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github#distributing-large-binaries).

О механизме выпусков: [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

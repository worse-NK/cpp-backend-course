# Защита курса: что именно усиливать

Учебник показывает страницы, сохраняет прогресс на устройстве и запускает
учебные модели. Он не просит ключ от GitHub или облака и не подключает личные
базы данных читателя. Но даже так важно контролировать, какой код загружается
в браузер и какие файлы попадают в публичный репозиторий.

Здесь объяснены меры, отмеченные аудитом, а не заявлено, что все они уже
включены. Отсутствие защитного слоя само по себе не доказывает взлом.

## 1. Внешние библиотеки и проверка целостности

Веб-страницы получают React и ReactDOM — библиотеки интерфейса — с unpkg.
Это CDN (чужой сервер, который раздаёт готовые файлы). Такой JavaScript
выполняется на странице курса, поэтому нельзя считать его менее доверенным
только потому, что он пришёл с другого сайта.

Указание версии `18.3.1` выбирает конкретный выпуск. HTTPS защищает соединение
с сервером, но не доказывает, что сам сервер отдаёт ожидаемый файл.
Если источник скомпрометируют, одного правильного адреса недостаточно.

Есть два основных способа уменьшить эту зависимость:

- Хранить проверенные библиотеки вместе с курсом. Так уже устроены приложение
  и новая локальная браузерная сборка; для их чтения CDN не требуется.
- Для внешнего файла задать SRI (проверку целостности по ожидаемому хешу).
  Браузер сравнивает полученные байты с указанной контрольной суммой и не
  исполняет скрипт, если подходящая проверка не проходит.

SRI не защищает от злоумышленника, который может одновременно заменить и
скрипт, и ожидаемый хеш в нашей странице. Самостоятельное хранение тоже не
отменяет проверку зависимостей и обновление их версий.

В текущем аудите содержимое CDN совпало с закреплёнными локальными копиями.
Это наблюдение в момент проверки, а не гарантия неизменности внешнего сервера.
Механизм проверки описан в
[рекомендации W3C SRI](https://www.w3.org/TR/2016/REC-SRI-20160623/).

## 2. CSP: какие действия разрешены странице

Представь, что на страницу случайно попал лишний тег со скриптом, который
пытается загрузиться с постороннего адреса. CSP (Content Security Policy,
политика безопасности содержимого) позволяет заранее сказать браузеру:
«исполнять скрипты только из перечисленных источников; для остальных — отказ».

Политика может отдельно ограничить скрипты, сетевые соединения, встроенные
страницы и другие ресурсы. Это дополнительный барьер на случай ошибки,
а не антивирус и не доказательство правильности всего разрешённого кода.

Для курса нельзя просто запретить всё: SQL-тренажёру нужен Worker
(отдельный поток выполнения JavaScript), а существующие страницы используют
определённые встроенные скрипты и стили. Совместимую политику нужно подготовить
по реальным ресурсам и проверить на лабораториях. Веб-страницы в большинстве
пока не задают собственную CSP; у приложения своя более строгая политика.

Политику передают в HTTP-заголовке или, с ограничениями, в HTML через `meta`.
Например, `frame-ancestors`, ограничивающий встраивание страницы другими сайтами,
через `meta` не работает. Поэтому нельзя обещать одинаковую защиту этих вариантов.
Подробности — в разделе
[Policy Delivery проекта CSP Level 3](https://www.w3.org/TR/CSP3/#policy-delivery).

## 3. Автоматическая проверка секретов

Один безопасный выпуск не мешает случайно добавить настоящий `.env` завтра.
Отдельная проверка при каждом изменении ищет похожие на ключи строки и
сообщает о них до выпуска. Gitleaks умеет проверять и текущие файлы, и историю.
Срабатывание надо разбирать: заголовок ключа в отрицательном тесте не является
самим ключом. Нельзя ради такого случая отключать проверку всех приватных ключей.

Важное ограничение: если проверка запускается в GitHub Actions **после push**,
данные уже отправлены на GitHub. Она помогает быстро обнаружить проблему и
остановить выпуск, но сама по себе не предотвращает первую публикацию секрета.
Для этого полезны локальные проверки перед отправкой и GitHub Push Protection
(блокировка поддерживаемых секретов на этапе push). Ни один детектор не
распознаёт любые возможные пароли и форматы ключей.

Если опубликован настоящий ключ, сначала отзывают или заменяют его у провайдера.
Удаление строки в новом коммите не делает старый ключ безопасным: он остаётся
в истории и мог быть скопирован. Переписывание публичной истории — отдельное
согласованное действие, а не автоматическая реакция на любой результат сканера.

Источники: [Gitleaks](https://github.com/gitleaks/gitleaks),
[GitHub Secret Scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning),
[Push Protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection).

## 4. Главная ветка и права автоматизации

Защита `main` может запретить принудительную замену истории или потребовать
успешных проверок перед слиянием. Это помогает не опубликовать случайно
непроверенную версию. Она не превращает загруженный секрет в закрытый и
не заменяет проверку его наличия в других ветках.

Публикация установщика использует временный `GITHUB_TOKEN`, который GitHub
предоставляет заданию Actions. В файле workflow хранится ссылка на токен,
а не его значение. Заданию сборки достаточно чтения; право `contents: write`
нужно заданию публикации, чтобы создать Release и загрузить вложения.
Личные токены для этой схемы не коммитят и не выводят в журналы.

Токен всё равно является полномочием: изменения workflow требуют такого же
внимания, как изменения программы. Используемые Actions закреплены по хешам
коммитов, а входные значения версии проверяются до сетевых операций.
См. [минимальные права GITHUB_TOKEN](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token).

Наличие исходного workflow не подтверждает настройки аккаунта, MFA или
Push Protection. Закрытые уведомления безопасности без авторизации не проверялись.

## 5. Email в истории — не ключ

В коммите есть имя и email автора. В публичном Git эти метаданные видны другим
людям. Адрес не даёт доступа к аккаунту, но его публикация может быть нежелательна.
Для будущих коммитов можно выбрать предоставленный GitHub адрес `noreply`.
Это не уберёт адрес из старых коммитов; историю без отдельного решения не меняем.

## Что не публиковать

Реальные `.env`, приватные ключи, профили браузера или приложения, cookies,
резервные копии прогресса и локальные `.state`-файлы не относятся к исходникам.
Список публикуемых файлов задаётся явно. `.gitignore` полезен, но не скрывает
уже отслеживаемые файлы и не заменяет проверку содержимого.

Пароли-заглушки в примерах предназначены для объяснения. Не переноси их в
рабочие сервисы. Безопасность настоящего сервера, базы и сети нужно проверять
отдельно: размещение учебника на GitHub Pages их не разворачивает.

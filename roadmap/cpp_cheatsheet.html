Класс: данные + методы

Класс объединяет состояние и операции; доступ проектирует автор

class Account {
    int balance_ = 0;
public:
    bool deposit(int amount) {
        if (amount <= 0 || amount > 1000000 - balance_)
            return false;
        balance_ += amount;
        return true;
    }
    int balance() const { return balance_; }
}; // инвариант: 0 <= balance_ <= 1000000

Инвариант (условие допустимого состояния объекта) в этом примере: баланс от 0 до 1000000. Конструктор создаёт допустимое состояние, а публичные операции обязаны его сохранять.

struct vs class

Отличие — в доступе по умолчанию

У struct члены и базовое наследование по умолчанию public, у class — private. В остальном возможности языка одинаковы.

Конструктор и деструктор

Конструктор = имя класса, задаёт начальное состояние (список инициализации)

class Point {
    int x, y;
public:
    Point(int x, int y) : x(x), y(y) {}  // список инициализации
};

Деструктор = ~ИмяКласса, вызывается автоматически при уничтожении

~Logger() { /* уборка */ }   // сам вызовется в конце области видимости

Порядок создания и уничтожения задаётся структурой объекта и областью видимости

Локальные объекты одной области видимости уничтожаются в обратном порядке завершённого создания. Поля инициализируются в порядке объявления в классе и уничтожаются в обратном; порядок в списке инициализации этого не меняет. База строится до полей и разрушается после них.

Несколько конструкторов

Конструкторов может быть несколько — с разными параметрами (перегрузка)

class Account {
    int balance;
public:
    Account() : balance(0) {}           // по умолчанию
    Account(int start) : balance(start) {}  // с балансом
};
Account a;       // -> balance 0
Account b(500);  // -> balance 500

Поля можно инициализировать прямо при объявлении (C++11)

class Timer {
    int ms = 0;        // значение по умолчанию
    bool running = false;
};

Инициализация и lifetime

{} помогает получить известное начальное значение и запрещает сужающие преобразования (narrowing)

int a;       // локальный a имеет indeterminate value: не читать
int b{};     // 0
int c{42};   // 42
// int d{3.14}; // ill-formed: narrowing double -> int

Выделенная память и живой объект — не одно и то же

Выделенная память (storage) ещё не обязательно содержит живой T, а окончание времени жизни объекта (lifetime) не всегда сразу освобождает память. В низкоуровневом коде отдельно отслеживают получение и освобождение памяти и отдельно — создание и уничтожение объектов в ней.

const и this

const-метод нельзя использовать для изменения обычных полей; его можно звать на const-объекте

Это shallow const: mutable-поля, внешнее состояние и объект за указателем всё ещё могут меняться. Логически читающие методы обычно помечай const, но не обещай ими больше, чем задаёт контракт.

this-> явно выбирает член, если параметр скрывает его имя

Account(int balance) : balance(balance) {}
// В теле: this->balance = balance;

Контракты конструктора

explicit, = default и = delete выражают намерение

class Id {
public:
    explicit Id(int value);       // нет неявного int -> Id
    Id() = delete;                 // пустой Id запрещён
    Id(const Id&) = default;       // обычное копирование явно разрешено
};

Конструктор должен установить инвариант или не создать объект

Если проверка не прошла, конструктор может бросить: уже построенные базы и поля разрушатся автоматически, но деструктор самого недостроенного объекта не вызывается.

Зачем инкапсуляция

private ограничивает прямой доступ, но инвариант сохраняет логика класса

Проверки в методах и конструкторах должны согласовываться. Возврат изменяемой ссылки на поле и friend могут открыть обходной путь; private само по себе не доказывает корректность.

Публичные методы — «пульт»; приватные поля — «провода»

Внутренности можно переписать, не ломая код, который пользуется классом через публичные методы.

Интерфейс, static и friend

Инвариант важнее набора getter/setter

Инвариант — условие корректного состояния объекта. Конструктор устанавливает его, публичные операции сохраняют. Не добавляй setter, если изменение поля в одиночку нарушит это условие.

static-член общий для класса; friend даёт доступ, но не членство

У static-метода нет this. Дружественная функция может читать private, но остаётся внешней функцией. Дружба не наследуется и не передаётся через цепочку друзей.

Равенство значений проектируют по смыслу

operator== обычно сравнивает значимые данные, а не адреса объектов. = default в C++20 сравнивает базы и поля: проверь, соответствует ли это смыслу равенства твоего типа.

RAII — сердце C++

Владение ресурсом выражается объектом, а освобождение — его деструктором

RAII (управление ресурсом через время жизни объекта-владельца) связывает освобождение с деструктором, в том числе при исключении. Владелец может быть пустым или получить ресурс позже; важно, чтобы каждое его допустимое состояние имело ясные правила освобождения.

Умные указатели (вместо new/delete)

unique_ptr — единоличное владение, нельзя копировать (только move)

auto p = std::make_unique<T>(args);
auto p2 = std::move(p);   // передать владение; p теперь nullptr

shared_ptr — разделяемое владение со счётчиком ссылок

auto a = std::make_shared<T>();
auto b = a;               // счётчик 2; удалится, когда счётчик -> 0

weak_ptr — невладеющий наблюдатель за shared_ptr (не держит объект живым)

std::weak_ptr<T> w = sp;   // из shared_ptr, счётчик НЕ растёт
if (auto s = w.lock()) {   // получить shared_ptr, если объект жив
    use(*s);
}

Правило выбора владения

Если объект можно хранить значением — храни значением. Нужны независимое от локальной области время жизни или полиморфизм с одним владельцем → unique_ptr. Реально несколько независимых владельцев → shared_ptr. Наблюдение за совместным владением и разрыв циклов → weak_ptr. Ручное управление владеющими new/delete в прикладном коде почти не нужно.

Ловушки shared ownership

Потокобезопасный управляющий блок shared_ptr не защищает сам T

Управляющий блок (control block — служебный объект со счётчиками владения и правилами освобождения) согласует работу разных shared_ptr. Разные экземпляры shared_ptr к одному блоку можно копировать и уничтожать одновременно, но доступ к *p синхронизируют по правилам самого T. Один и тот же shared_ptr нельзя произвольно читать и изменять без синхронизации.

make_shared обычно выделяет память для объекта и управляющего блока вместе

Совместное выделение уменьшает число обращений к распределителю памяти. После исчезновения сильных владельцев объект разрушен, но общая память может сохраняться до исчезновения weak_ptr. Если нужны отдельное время жизни памяти или свой удалитель (функция освобождения ресурса), выбирай другой способ осознанно.

Цикл shared_ptr не освобождается сам

// Parent владеет Child, а обратная связь наблюдает:
std::shared_ptr<Child> child;
std::weak_ptr<Parent> parent;

Ссылки и const

Тяжёлые объекты передавай как const T& (без копии, только чтение)

void f(const std::string& s);   // не копирует, не меняет

Ссылка — псевдоним: после связывания её нельзя переназначить

В корректной программе ссылка связывается с объектом или функцией, а не с null. После окончания времени жизни объекта ссылка может стать висячей (dangling — больше не дающей доступа к живому объекту). Одно наличие T& не доказывает, что объект ещё существует.

auto, decltype и forwarding

auto по значению не сохраняет ссылку и const самого копируемого значения

const int n = 7;
auto a = n;        // int
const auto& r = n; // const int&
auto&& u = n;      // const int& из-за reference collapsing
decltype(auto) x = (n); // const int&: скобки важны

Forwarding reference: T&& с выводимым cv-неквалифицированным параметром шаблона

template<class T>
void relay(T&& value) {
    consume(std::forward<T>(value));
}
// Widget&& вне такого deduction context — обычная rvalue reference.

Move-семантика

Move-операция может передать ресурсы вместо копирования; std::move лишь разрешает её выбрать

v.push_back(std::move(s));  // s валиден, но его состояние обычно не специфицировано

std::move сам ничего не двигает

std::move даёт выражение категории xvalue (обозначает существующий объект, ресурсы которого разрешено передать). Это позволяет выбрать перемещающую операцию, но не вызывает её само по себе и не снимает const.

Правило пяти / нуля

Правило нуля (предпочтительно): не управляй ресурсами вручную

Используй vector/string/unique_ptr и другие RAII-члены — тогда обычно не нужно писать пять спецфункций. Компилятор сгенерирует, удалит или не объявит конкретную операцию по правилам членов: например, unique_ptr естественно удаляет копирование. Проверяй именно нужные свойства типа.

Правило пяти: объявление одной спецфункции требует проверить остальные

Для каждой операции реши явно: реализовать, = default или = delete. Уникальный ресурс часто только перемещаем, а копирование запрещено.

Синтаксис

auto, range-for, лямбды

for (const auto& x : v) { ... }        // чтение
for (auto& x : v) { x *= 2; }           // изменение
auto f = [](int a, int b){ return a+b; };

Возврат значений и заимствование

return T{…} и return local — разные случаи

В C++17+ возврат prvalue того же типа (выражения, непосредственно инициализирующего результат) может создавать результат без промежуточной копии. NRVO (устранение копирования именованного локального результата) разрешено, но не обязательно. return std::move(local) мешает NRVO; обычно достаточно return local.

Захват ссылки не продлевает жизнь объекта

Лямбда с [&] или [this] может пережить объект, на который ссылается. Для отложенной задачи проверь владельца каждого захвата. Копирование string_view копирует только представление, а не строку.

После перемещения действуй по контракту типа

У стандартных библиотечных типов обычно сохраняется корректное, но не определённое заранее состояние. unique_ptr после передачи владения пуст; для string не обещай пустоту. У пользовательского типа гарантии задаёт его автор.

Наследование

class Derived : public Base — отношение is-a

class Dog : public Animal {
public:
    Dog(const std::string& n) : Animal(n) {}  // вызвать конструктор базы
};

protected — доступно классу и наследникам, но не снаружи

Третий уровень между private и public.

Порядок: строятся базовые подобъекты, затем Derived; разрушение идёт обратно

У самого derived-типа сначала строятся virtual bases, затем direct bases слева направо, затем поля в порядке объявления и тело. Деструктор выполняет обратную последовательность для уже построенных подобъектов.

Виртуальные функции = полиморфизм

virtual в базе + override в наследнике → динамический вызов

class Animal {
public:
    virtual void say();
    virtual ~Animal() = default;
};
class Dog : public Animal { public: void say() override; };

auto p = std::make_unique<Dog>();
Animal& animal = *p;
animal.say();   // final overrider: Dog::say()

Runtime-полиморфизм обычно используют через указатель/ссылку на базу

Animal&, Animal*, unique_ptr<Animal>. Передача производного объекта как Animal по значению создаёт отдельный базовый объект и срезает derived-часть.

Абстрактные классы (интерфейсы)

= 0 делает функцию чисто виртуальной, класс — абстрактным

class Shape {
public:
    virtual double area() const = 0;   // объект Shape создать нельзя
    virtual ~Shape() = default;
};

Две частые ловушки

Virtual-деструктор нужен базе для полиморфного удаления

Если производный объект удаляют через Base*, деструктор базы должен быть virtual; иначе delete имеет UB. Само наличие virtual-метода не доказывает, что такое удаление разрешено дизайном.

Срезка (slicing): по значению теряется часть наследника

Dog d;
Animal a = d;   // Dog-часть отрезана, полиморфизм сломан
// храни полиморфно: vector<unique_ptr<Animal>>

Lookup, default arguments и downcast

Имя в Derived скрывает весь overload set Base с тем же именем

struct Base { void f(int); void f(double); };
struct Derived : Base {
    using Base::f;       // вернуть overloads базы в lookup
    void f(std::string);
};

Virtual body выбирается динамически, default argument — по static type

Не меняй default arguments при override: вызов через Base& возьмёт default из объявления Base, даже если выполнится тело Derived. Лучше передать аргумент явно или использовать non-virtual interface.

dynamic_cast проверяет полиморфный downcast во время выполнения

Для pointer неудача даёт nullptr, для reference — std::bad_cast. Это инструмент на границе неоднородной иерархии, а не замена хорошему virtual-интерфейсу; база должна быть polymorphic.

Типичная реализация virtual

vptr/vtable — распространённая ABI-модель

Большинство ABI использует vptr/vtable, но стандарт требует только поведение динамического вызова и не предписывает внутреннюю таблицу.

Порядок вызовов и исключения

Строительство: virtual bases → direct bases → fields → тело; разрушение обратно

Инициализаторы баз и полей вычисляются по правилам языка, но сами подобъекты строятся в предписанном порядке, не по строкам initializer list. При исключении разрушаются только полностью построенные подобъекты.

Virtual-вызов в конструкторе/деструкторе не уходит в ещё не живущую derived-часть

Во время конструктора/деструктора dispatch ограничен текущей строящейся или разрушающейся частью иерархии. Прямой или косвенный вызов pure virtual для строящегося/разрушающегося объекта из ctor/dtor даёт undefined behavior — это не способ вызвать реализацию наследника.

Выбор полиморфного интерфейса

Композиция — содержит; публичное наследование — подставляется вместо

Если нужен только готовый код базы, отношение is-a из этого не следует. Скрывай делегирование в поле; наследование оставь для осмысленной взаимозаменяемости по контракту.

clone сохраняет динамический тип копии

В интерфейсе можно вернуть unique_ptr<Base>; наследник создаёт копию себя через make_unique<Derived>(*this). unique_ptr<Derived> не является ковариантным возвращаемым типом для override — сигнатура остаётся unique_ptr<Base>.

vector — контейнер по умолчанию

Динамический массив, непрерывная память

std::vector<int> v;
v.push_back(10);          // добавить элемент
v.size(); v[0]; v.at(0);  // [] без проверки, at() бросает при выходе
v.reserve(1000);          // capacity >= 1000, size не меняется
v.resize(1000);           // size = 1000: элементы реально созданы

Инвалидация зависит от операции и reallocation

При reallocation у vector инвалидируются все ссылки, указатели и итераторы. Без reallocation вставка инвалидирует как минимум old end и позиции от места вставки. erase инвалидирует удалённые и всё после них. Перед сохранением iterator всегда проверь правило конкретной операции.

map / unordered_map / set

map — O(log n) и порядок; unordered_map — O(1) в среднем, O(n) в худшем

std::map<std::string,int> m;
++m["key"];   // [] создаёт ключ с 0, если его нет

Ловушка operator[]: создаёт ключ, если его нет

Для проверки наличия — m.contains(key) (C++20) или m.find(key) != m.end().

set — уникальные значения в порядке comparator

«Уникальность» определяется эквивалентностью comparator: ни comp(a,b), ни comp(b,a). Comparator обязан задавать strict weak ordering.

Стабильность и контракты контейнеров

Node-based containers обычно сохраняют ссылки на не удалённые элементы

У map/set/list вставка не инвалидирует references/iterators, а erase инвалидирует удалённое. У unordered_* rehash инвалидирует iterators, но не references/pointers на элементы; erase инвалидирует только удалённое. У deque правила зависят от операции — проверяй отдельно.

Comparator обязан задавать strict weak ordering

// плохо: <= не является строгим порядком
// std::sort(v.begin(), v.end(), [](auto a, auto b){ return a <= b; });

// обычно:
std::sort(v.begin(), v.end(), std::less{});

emplace — интерфейс построения, а не обещание «всегда быстрее»

Он передаёт аргументы конструктору элемента, но копии/move, временные объекты и стоимость проверки зависят от контейнера и вызова. Для map, когда не хочешь строить mapped value при существующем ключе, смотри try_emplace.

Итераторы

Полуоткрытый диапазон [begin, end)

end() указывает ЗА последним элементом — не разыменовывать. Цикл: it != end().

Алгоритмы <algorithm>

sort, find, count_if, transform, max_element

std::sort(v.begin(), v.end());               // по возрастанию
std::sort(v.begin(), v.end(),
          [](int a,int b){ return a>b; });   // свой компаратор
std::count_if(v.begin(), v.end(),
              [](int x){ return x>0; });     // подсчёт по условию
auto it = std::find(v.begin(), v.end(), 8);  // вернёт итератор или end()

Шаблоны

Функция: template<typename T>

template<typename T>
T myMax(T a, T b) { return a > b ? a : b; }

Аргументы шаблона можно указать явно; с C++17 иногда работает вывод CTAD

template<typename T>
class Box { T value; public: Box(T v):value(v){} };
Box<int> b(42);

Определение шаблона обычно должно быть доступно при инстанцировании

Поэтому template definitions обычно лежат в header. Разнести можно через явные instantiation definitions для заранее выбранного набора типов.

Современные удобства

optional, structured bindings, auto

std::optional<int> r = find();
if (r) use(*r);                 // значение или nullopt

for (const auto& [key, val] : m) { ... }  // распаковка пары

Ranges, concepts и non-owning view

Ranges принимают диапазон целиком и поддерживают projection

auto it = std::ranges::find(users, id, &User::id);
std::ranges::sort(users, std::less{}, &User::name);

Concept делает требования шаблона частью интерфейса

template<class T>
concept Number = std::integral<T> || std::floating_point<T>;

template<Number T> T twice(T value) { return value + value; }

string_view/span не владеют памятью

Они дешевы для параметров и срезов, но источник обязан жить дольше view. Не возвращай string_view на временную string и не храни span после уничтожения/reallocation контейнера.

Erase и выбор контейнера

Удаляй из vector безопасным API

std::erase_if(values, [](int x) { return x < 0; }); // C++20

for (auto it = m.begin(); it != m.end(); ) {
    if (expired(*it)) it = m.erase(it);
    else ++it;
}

Big O — не вся стоимость

Учитывай locality, аллокации, размер элемента, стабильность адресов и профиль операций. vector остаётся первым кандидатом; list/unordered_map выбирай по требуемому контракту и измерениям.

Выбор типа результата и поиск

optional, variant и expected отвечают на разные вопросы

optional<T> — значение или отсутствие; variant<A,B> — одно из перечисленных состояний; expected<T,E> (C++23) — успех или ошибка с причиной. Для variant обработай варианты через visit; get неверного активного типа бросает bad_variant_access.

Бинарный поиск требует подходящего порядка

lower_bound требует разбиения диапазона относительно искомого значения и компаратора; сортировка тем же компаратором обеспечивает это для всех запросов. Для forward-итераторов число сравнений логарифмическое, но перемещений итератора может быть линейно.

Базовый механизм

throw бросает, try/catch ловит; между ними стек разматывается

try {
    risky();
} catch (const std::out_of_range& e) {   // конкретный — первым

    std::cerr << e.what();
}

Объекты иерархии исключений обычно ловят по const-ссылке

catch (const std::exception&) — без slicing и с полиморфным what(). Порядок catch: от конкретного к общему. Для повторного выброса используй throw;, а не throw e;.

Иерархия во главе с std::exception

std::bad_alloc                // бросает new при нехватке памяти

class CollectorError : public std::runtime_error {
public:
    explicit CollectorError(const std::string& m)
        : std::runtime_error(m) {}
};

throw CollectorError("cannot open /proc/meminfo");

RAII + исключения

При раскрутке стека деструкторы вызываются — ресурсы освобождаются сами

void f() {
    std::ifstream file("x");   // RAII
    throw std::runtime_error("err");
}   // деструктор file вызовется -> файл закрыт

RAII-деструктор не должен выпускать исключение наружу

Язык допускает potentially-throwing destructor, но исключение из него при раскрутке другого исключения приводит к std::terminate. Проверяемую ошибку закрытия сообщай отдельным close()/commit().

Гарантии безопасности

Четыре уровня, от слабого к сильному

no guarantee — после исключения контракт состояния не обещан (это не автоматически UB); basic — инварианты сохранены и утечек нет, конкретное состояние может быть unspecified; strong — охваченный контрактом наблюдаемый эффект «всё или ничего»; no-throw — исключение не выходит к вызывающему. Внешний I/O и другие необратимые эффекты сильная гарантия сами по себе не откатывает.

copy-and-swap — идиома для строгой гарантии

void update(Config& cfg, const Data& d) {
    Config tmp = cfg;      // работаем на копии
    tmp.apply(d);          // если бросит — состояние cfg прежнее
    using std::swap;
    swap(cfg, tmp);        // strong для cfg, если swap noexcept
}
// Файлы/сеть, изменённые tmp.apply(), автоматически не откатятся.

noexcept

Обещание не бросать; нарушил — terminate

void swap(T& o) noexcept;
T(T&& o) noexcept;              // move-конструктор
T& operator=(T&& o) noexcept;   // move-присваивание

Зачем: vector перемещает вместо копирования

Если move noexcept, vector может безопасно перемещать. Иначе для копируемого типа часто выберет копию; move-only тип всё равно придётся перемещать.

Выбор error channel

Тип результата должен различать нужные вызывающему исходы

std::optional<Metric> find(Key); // ожидаемое отсутствие, без причины
std::expected<Config, ParseError> parse(std::string_view); // C++23
std::error_code removeFile(Path) noexcept; // явный системный status

Config loadRequired(Path); // может throw: операция не может продолжаться

expected<T,E> — обычная часть контракта, exception — нелокальный выход

Не выбирай по лозунгу или предполагаемой скорости. Учитывай частоту исхода, необходимость причины, composability, ABI и политику проекта. На request/thread/C ABI границе исключение поймай и преобразуй в документированную ошибку.

Ошибка на границе сервиса

Ошибка клиента, временный сбой и баг требуют разных действий

Неверные данные верни как документированную ошибку; временный сбой оцени с учётом бюджета повторов; нарушение инварианта расследуй. catch (...) не означает, что можно безопасно продолжить любую операцию.

Таймаут не доказывает отсутствие эффекта

Сервер мог выполнить запись, а ответ потеряться. Повтор безопасен только при соответствующем контракте операции или дедупликации. Один deadline (предельный момент завершения) ограничивает суммарное ожидание всех попыток.

Этапы компиляции

Практический toolchain: препроцессинг → компиляция → ассемблирование → линковка

В типичном native toolchain препроцессор обрабатывает директивы, compiler формирует код (часто через assembly/IR), assembler создаёт object file, linker соединяет objects и библиотеки. Это удобная модель GCC/Clang, а не требование ISO C++ обязательно сохранять отдельный .s на диске; драйвер обычно скрывает промежуточные шаги.

undefined reference = ошибка линковки

Linker не нашёл подходящий символ. Причина может быть в отсутствующем definition/.cpp/library, несовпавшей сигнатуре или language linkage, порядке/режиме линковки либо visibility — смотри полное имя символа и команду link.

ODR, linkage и ABI

Обычное external non-inline definition должно быть одним на программу

Функция с телом в подключаемом header обычно даст multiple definition. inline разрешает эквивалентные definitions в разных translation units; это правило ODR, а не команда оптимизатору. Include guard действует только внутри одной TU.

Linkage и symbols объясняют ошибки линкера

namespace { void helper(); } // internal linkage в этой TU

Гонка данных

Несинхронизированный ++ обычного общего counter — UB

В учебной модели ++ содержит чтение, вычисление и запись; это не обещание трёх конкретных машинных инструкций. При конфликтующих неатомарных доступах без установленного порядка возникает гонка данных — UB (неопределённое поведение: стандарт не задаёт требования к результату), а не просто неточность счётчика.

Виды мьютексов

Четыре типа под разные задачи

mutex — базовый выбор для взаимного исключения. recursive_mutex — повторный захват тем же потоком. timed_mutex — ждать с таймаутом (try_lock_for). shared_mutex (C++17) — много читателей ИЛИ один писатель.

shared_mutex: читают часто, пишут редко

std::shared_mutex m;

// Фрагмент читателя:
{ std::shared_lock lock(m); /* чтение */ }

// Фрагмент писателя:
{ std::unique_lock lock(m); /* изменение */ }
// Это два отдельных критических участка, не upgrade блокировки.

RAII-обёртки

Четыре обёртки — ручные lock/unlock не пиши

std::lock_guard<std::mutex> l(m);    // по умолчанию, весь блок
std::unique_lock<std::mutex> l(m);   // гибкая: unlock/lock, defer
std::scoped_lock l(m1, m2);          // deadlock-avoiding общий захват
std::shared_lock l(sharedMutex);     // читатель shared_mutex

Мьютекс — поле рядом с данными

class Registry {
    std::vector<Metric> data_;
    mutable std::mutex mutex_;   // mutable для const-методов
public:
    std::size_t size() const {
        std::lock_guard lock(mutex_);   // чтение тоже защищаем
        return data_.size();
    }
};

Deadlock

Причина — разный порядок захвата

A держит m1, ждёт m2; B держит m2, ждёт m1 → висят вечно.

Четыре способа избежать

(1) единый порядок захвата везде; (2) std::scoped_lock для нескольких; (3) не вызывать чужой/виртуальный код под блокировкой; (4) меньше мьютексов и вложенности.

std::atomic

Операции атомарны; lock-free зависит от типа и реализации

std::atomic<int> c{0};
++c;                    // атомарно; lock-free проверяется отдельно
c.load(); c.store(5);
c.fetch_add(3);
c.exchange(7);          // записать, вернуть старое

int exp = 7;
c.compare_exchange_strong(exp, 10);   // CAS: основа lock-free

atomic или mutex

Независимый счётчик или флаг часто выражается atomic RMW. Составной инвариант, check-then-act или несколько полей обычно проще защищать mutex. Atomic load + отдельный store не образуют транзакцию; «atomic быстрее» без benchmark не гарантируется.

memory_order

Memory order задаёт гарантии atomic-операции, а не корректность всей программы

seq_cst — по умолчанию и единый total order для seq_cst atomic-операций; он не чинит data race на обычной памяти. relaxed — атомарность/modification order без публикации соседних данных. Release synchronizes-with acquire, только когда acquire прочитал опубликованное значение (или release sequence). Ослабляй порядок лишь с доказанным happens-before и измеренной причиной.

Happens-before: быстрый алгоритм проверки

Data race: конфликтующие потенциально одновременные доступы, хотя бы один неатомарный, без happens-before

Нарисуй действия двух потоков. Внутри потока есть sequenced-before. Мост дают synchronizes-with: unlock → следующий lock того же mutex; release → acquire, прочитавший публикацию; завершение thread → успешный join. Транзитивная цепочка даёт happens-before. Моста нет — UB, а не просто «старое значение».

join публикует результат завершившегося worker

int result = 0;
std::thread worker([&] { result = 42; });
worker.join();
use(result); // запись worker happens-before чтения после join

condition_variable

Спать до события вместо busy waiting

// Общие m, cv, q и closed живут дольше обоих потоков.
// Consumer (отдельный поток):
{
    std::unique_lock lock(m);
    cv.wait(lock, [&] { return closed || !q.empty(); });
    // Под lock: извлечь элемент или обработать closed + empty.
}

// Producer (другой поток):
{ std::lock_guard lock(m); q.push(x); }
cv.notify_one(); // уведомление не хранит само состояние
// Полный протокол очереди также проверяет closed перед push.

Почему unique_lock и предикат

wait отпускает мьютекс на время сна и берёт обратно — lock_guard так не умеет. Предикат нужен из-за ложных пробуждений (поток может проснуться сам).

future / promise / async

std::async связывает задачу с future, но не задаёт ограниченный пул

auto f = std::async(std::launch::async, work, arg);
int result = f.get();   // ждёт, получает value или повторно бросает exception

// Без явной policy реализация вправе выбрать deferred.
// Освобождение последней ссылки на async shared state может ждать задачу;
// временные future способны сериализовать последовательные вызовы.

promise/future — канал для результата вручную

std::promise<int> p;
std::future<int> f = p.get_future();
std::thread t([p = std::move(p)]() mutable {
    p.set_value(42);
});
t.join();

future переносит сохранённое исключение задачи

try {
    auto v = f.get(); // shared state повторно бросит exception здесь
} catch (const CollectorError& e) { log(e.what()); }

// Непойманное исключение из обычной thread function -> terminate.

get() — один раз

После future::get() future больше не valid; второй get нарушает предусловие. Для нескольких получателей/чтений используют std::shared_future.

packaged_task — задача-объект без автозапуска

Оборачивает функцию + future, но не запускает: можно положить в очередь. Основа пулов потоков.

Примитивы C++20

Семафор — счётчик разрешений

std::counting_semaphore<4> limit(4);
limit.acquire();   // взять (ждёт, если нет)
// ... не более 4 потоков здесь ...
limit.release();   // вернуть

std::binary_semaphore sig(0);   // сигнализация между потоками

latch — одноразовый счётчик обратного отсчёта

std::latch done(3);
done.count_down();      // «я закончил» (в каждом потоке)
done.wait();            // ждём, пока все три отчитаются

barrier — многоразовый, для повторяющихся фаз

std::barrier sync(3, []() noexcept { publishNoThrow(); });
// в цикле каждого потока:
sync.arrive_and_wait();   // ждём всех и completion, потом идём дальше

Прочее полезное

call_once — ровно одно успешно завершившееся выполнение

std::once_flag flag;
std::call_once(flag, initConfig);  // после исключения следующая попытка повторит вызов

// проще для простых случаев:
Config& get() { static Config c = load(); return c; }  // синхронизирована инициализация, не все обращения к c

thread_local — отдельный объект на поток

Сам thread_local-объект обычно не разделяется, но указатель на него можно передать другому потоку, а его поля могут ссылаться на общее состояние. Поэтому отсутствие синхронизации следует из отсутствия совместного доступа, а не только из ключевого слова.

false sharing — переменные в одной кэш-линии

Разные потоки меняют соседние объекты → coherence может гонять одну cache line без data race. Универсального размера 64 стандарт не обещает: ориентир — std::hardware_destructive_interference_size, а необходимость padding подтверждай размещением и benchmark.

Потокобезопасный API и shutdown

Два thread-safe метода не образуют атомарную операцию

// TOCTOU: между вызовами другой consumer меняет очередь
if (!q.empty()) q.pop();

// контракт лучше выразить одной линейризуемой операцией
std::optional<T> try_pop();

Не возвращай reference/iterator, защита которого кончилась вместе с lock

После unlock другой поток может изменить или удалить объект. Верни snapshot/value либо предоставь одну операцию под lock с документированным запретом re-entry/callback-риском.

Очереди нужны close и backpressure

Bounded queue ограничивает память и явно выбирает overload policy: block, reject, timeout или drop. Shutdown: запретить новые задачи → разбудить ожидающих/request_stop → drain/cancel по контракту → join workers → разрушить их зависимости. stop_token кооперативен и не прерывает произвольный blocking syscall.

Проверка конкурентного кода

TSan — динамический детектор, не доказательство

c++ -std=c++20 -O1 -g -fsanitize=thread \
    -fno-omit-frame-pointer test.cpp -pthread
./a.out

Три слоя уверенности

(1) Инварианты, lifetime и граф happens-before; (2) направленные тесты + barriers/latches + stress + TSan; (3) production metrics: queue depth, lock wait, active workers, timeout/drop и shutdown latency. Нельзя benchmark-ить UB.

Как выбрать инструмент

Быстрый ориентир

Одна/несколько независимых задач с результатом → future/async; постоянный или bounded поток работ → очередь + pool/executor. Общие данные → mutex + RAII lock. Независимый счётчик/флаг → atomic. Много чтений, редкая запись → кандидат shared_mutex после измерения. Ждать изменения состояния → condition_variable. Ограничить одновременный вход → semaphore. Дождаться группы → latch. Повторять синхронные фазы → barrier. Сначала формулируй invariant/lifetime/shutdown, затем выбирай примитив.

CAS, ожидание и пределы ускорения

compare_exchange обновляет expected при неудаче

CAS сравнивает значение с expected; при несовпадении записывает фактическое значение в expected. weak может отказать ложно — обычно нужен цикл. Успех одного CAS не решает lifetime узлов: ABA и освобождение памяти требуют отдельного протокола.

atomic::wait ждёт изменения значения, а не запоминает события

В C++20 сначала меняют atomic, затем вызывают notify_one/all. Уведомление без изменения значения не гарантирует выход из wait; переход A → B → A может быть не замечен. Для очереди задач нужен счётчик или предикат состояния.

Больше потоков не означает меньше задержку

Если доля p работы распараллеливается, идеальная оценка ускорения на N исполнителях: 1 / ((1 − p) + p/N). При p = 0,9 и N = 4 это около 3,08. Реальные блокировки, планировщик и обмен данными обычно снижают выигрыш.

7.1 · Путь запроса: имя, адрес, соединение

DNS разрешает имя; маршрутизация доставляет IP-пакеты

DNS-ответ может прийти из кэша; имя может иметь несколько адресов. Порт выбирает транспортную конечную точку, а не URL-путь. HTTP-путь разбирает уже приложение. Проверяй DNS, соединение, TLS и HTTP как отдельные этапы.

localhost относится к текущему сетевому окружению

127.0.0.1 и ::1 — loopback; внутри контейнера это обычно сам контейнер. Bind на 0.0.0.0 означает все локальные IPv4-интерфейсы, а не адрес, который клиент должен использовать.

7.2 · Что добавляют сетевые уровни

Инкапсуляция добавляет служебные поля, а не новые HTTP-запросы

Для обычного HTTP/1.1 поверх TCP: байты HTTP → TCP-заголовок и часть потока → IP-заголовок → кадр канального уровня. При HTTPS между HTTP и TCP находятся TLS records. Границы HTTP-сообщений, TLS records, TCP-сегментов и кадров не обязаны совпадать.

MTU ограничивает пакет на канале

TCP делит поток на сегменты; IP и транспортные заголовки занимают часть доступного размера. MTU, MSS и размер буфера recv — не одно и то же. По одному маленькому recv нельзя заключить, что отправитель послал маленькое сообщение.

7.3 · TCP, UDP и QUIC

TCP — упорядоченный поток байтов, не очередь сообщений

Запиши протокол границ: длина, разделитель с экранированием или готовый HTTP-парсер. Успешный send ещё не означает, что сервер обработал команду; для этого нужен ответ уровня приложения.

UDP сохраняет границы датаграмм, но не обещает доставку

Потери, дубликаты и перестановки учитываются протоколом приложения. QUIC работает поверх UDP, добавляет защищённые соединения и надёжные потоки; потеря данных одного потока не требует упорядочивать с ним доставку других, хотя общая перегрузка влияет на соединение.

7.4 · POSIX sockets: чтение и запись

Частичные операции — нормальный результат

send может принять лишь часть буфера: сохрани смещение. Для TCP recv с ненулевым размером буфера возвращает >0 байты, 0 — EOF, -1 — ошибку. EINTR и EAGAIN/EWOULDBLOCK обрабатываются по режиму операции; EOF не обязательно означает, что ты уже закончил отправку.

У сокета должен быть владелец

Закрывай descriptor ровно один раз RAII-объектом. Для неблокирующего connect EINPROGRESS — начало ожидания; после готовности проверь SO_ERROR. Учти SIGPIPE при записи в закрытое соединение; способ подавления зависит от платформы.

7.5 · epoll: готовность не равна завершению

Событие разрешает попробовать I/O без блокировки

В режиме edge-triggered используй неблокирующие дескрипторы и обслуживай чтение/запись до EAGAIN; иначе можно не получить нового ребра. Если вводишь квоту ради справедливости, сохрани готовую работу и явно запланируй её продолжение.

Не подписывайся постоянно на запись без данных

EPOLLOUT часто готов: включай интерес, когда есть неотправленный буфер, и снимай после его опустошения. Не выполняй долгий CPU-код или блокирующий вызов в event loop.

7.6 · Boost.Asio и время жизни

Буфер обязан дожить до completion handler

async_write не делает владельцем переданный buffer. Состояние сессии должно хранить данные до завершения; не запускай пересекающиеся составные записи в один stream. Очередь исходящих сообщений делает порядок явным.

strand сериализует обработчики, но не привязывает к одному потоку

Все обращения к защищаемому состоянию должны идти через тот же strand или другой согласованный механизм. Таймер, отмена и completion могут конкурировать логически: заверши запрос один раз, а оставшиеся callbacks обработай безопасно.

7.7 · HTTP framing и TLS

Границы HTTP/1.1 разбираются по правилам протокола

Пустая строка заканчивает заголовки, не обязательно тело. Длина зависит от статуса, метода и полей framing; противоречивые длины опасны для proxy и backend. Не пиши production HTTP-парсер из нескольких split.

TLS шифрует канал, но не заменяет проверку прав

Проверь доверие сертификату и имя сервера; не отключай verification ради исправления ошибки. TLS может завершаться на reverse proxy: отдельно защити следующий участок и доверяй forwarded-заголовкам только от известного proxy.

HTTP/2 и HTTP/3 меняют транспорт сообщений

HTTP/2 использует потоки внутри одного TCP-соединения; потеря TCP-сегмента может задержать их все. HTTP/3 работает поверх QUIC. Версия протокола сама по себе не исправляет медленный обработчик или неограниченную очередь.

7.8 · Нагрузка, таймауты и диагностика

Backpressure ограничивает накопление работы

Задай пределы на соединения, тело запроса, очередь и исходящий буфер. При превышении явно выбери отказ, ожидание в пределах deadline или сброс по контракту. Иначе медленный клиент способен удерживать память без границы.

Проверяй и пропускную способность, и хвост задержек

Для устойчивой системы L = λW: среднее число запросов в системе равно средней интенсивности поступления, умноженной на среднее время в ней. 200 запросов/с × 0,05 с = 10 запросов. Это средние, не формула p99 и не гарантия устойчивости при перегрузке.

Диагностика идёт от внешнего симптома к узкому месту

curl -v помогает увидеть этап HTTP/TLS, ss — сокеты, tcpdump — пакеты при нужных правах. На сервере сопоставь latency, ошибки, CPU, очередь и время зависимостей. Не записывай токены и тела с секретами в диагностический лог.

8.1 · Контракт API

API обещает поведение, а не только JSON

Зафиксируй методы, пути, типы полей, ошибки, права, лимиты и повторы. HTTP+JSON ещё не означает соблюдение всех ограничений REST. Stateless означает отсутствие необходимости в скрытом контексте прошлых запросов на сервере, а не запрет хранения ресурсов.

8.2 · Методы и статусы

Безопасность и идемпотентность — разные свойства

GET/HEAD не запрашивают изменение состояния; PUT и DELETE идемпотентны по ожидаемому эффекту. Повторный DELETE может дать другой статус. POST и PATCH не идемпотентны автоматически; свойство можно обеспечить контрактом.

Ответ должен соответствовать факту

201 — ресурс создан; 202 — принят, но ещё не завершён; 204 — без содержимого. 400 — некорректный запрос, 404 — ресурс не найден, 409 — конфликт состояния, 412 — не выполнено условие запроса. 401 требует подходящего WWW-Authenticate; 403 — отказ в доступе.

8.3 · Валидация и ошибки

Проверяй вход слоями

Сначала лимит байтов и Content-Type, затем синтаксис JSON, типы/диапазоны, после этого бизнес-условия. Пропущенное поле, null и пустая строка могут означать разное. Не превращай любое исключение парсинга и бизнес-логики в один и тот же 500.

Ошибка должна помогать клиенту, но не раскрывать внутренности

Problem Details (RFC 9457) задаёт application/problem+json и поля type, title, status, detail, instance. Это формат, не каталог всех ошибок. Добавляй машинно-читаемые детали валидации по контракту; не выдавай stack trace, пароли и SQL.

8.4 · Слои C++-сервиса

Handler переводит HTTP, сервис выполняет правило, хранилище держит данные

Handler разбирает запрос и формирует ответ. Сервис проверяет бизнес-инвариант. Хранилище обеспечивает согласованный доступ. Не возвращай ссылку на элемент, который другой запрос может удалить после отпускания lock.

Память процесса — не долговечное хранилище

Mutex защищает данные только внутри согласованного процесса. Перезапуск теряет in-memory задачи, несколько реплик имеют разные копии. Не обещай сохранность и общую дедупликацию без механизма, который действительно это обеспечивает.

8.5 · Конкурентные изменения и повторы

Проверка версии и запись должны быть одной операцией

ETag/If-Match помогают обнаружить изменение после чтения. Но сервер должен атомарно проверить версию и применить запись; отдельные find и update всё ещё допускают lost update. При несовпадении предусловия верни 412.

Ключ идемпотентности требует серверного протокола

Свяжи ключ с пользователем, операцией и содержимым запроса. Определи срок хранения, ответ на другой payload с тем же ключом и одновременные повторы. Фиксация эффекта и результата дедупликации не должна оставлять окно для двойной операции.

Повторы ограничены общим бюджетом

Используй backoff (увеличивающуюся паузу перед повтором) с jitter (случайным разбросом задержки), предел попыток и общий deadline (предельный момент завершения). Не повторяй заведомо неверный ввод. Если ответ потерян, сначала учитывай возможность уже выполненного эффекта.

8.6 · Доверие и авторизация

Знать пользователя недостаточно: проверь доступ к объекту

Аутентификация отвечает «кто», авторизация — «что разрешено». Проверяй владельца/tenant каждой записи и операции; случайный ID не является защитой. Проверяй подпись и необходимые claims токена по принятой политике.

CORS не защищает API от небраузерных клиентов

CORS — правила браузера о доступе к ответу другого источника (origin: схема, хост и порт). CSRF (подделка запроса с полномочиями жертвы) касается запросов с автоматически прикрепляемыми учётными данными, например cookie. Нужны соответствующие SameSite/CSRF-меры; TLS и CORS их не заменяют.

8.7 · Совместимость, списки и кэш

Новый обязательный параметр может сломать старого клиента

Версионируй поведение осознанно. Зафиксируй схему и примеры в OpenAPI, проверь контрактными тестами. Даже добавление enum-варианта может сломать клиента, который не умеет обрабатывать неизвестное значение.

Пагинация требует устойчивого порядка

Offset (пропуск заданного числа строк) прост, но при изменениях возможны пропуски и повторы. Cursor (указатель позиции для следующей страницы) должен учитывать сортировку и уникальное дополнительное поле при равенстве основных ключей; сам по себе он не даёт неизменного снимка данных. Ограничь размер страницы и проверяй содержимое курсора.

Кэширование — часть контракта ответа

no-cache требует проверки перед повторным использованием, а no-store запрещает хранение. Для условного GET валидатор помогает ответить 304 без содержимого. Учитывай персональные данные и Vary: общий кэш не должен смешать ответы разных пользователей.

8.8 · Асинхронные операции и события

202 — это обещание принять работу, а не выполнить её успешно

Верни способ узнать статус операции: pending/running/succeeded/failed и результат по контракту. Определи срок хранения, отмену и поведение после рестарта. Webhook требует проверки отправителя и защиты от повторной доставки.

SSE, WebSocket и polling решают разные задачи

Polling проще, но создаёт повторные запросы. SSE подходит для потока событий сервер → клиент, WebSocket — для двустороннего обмена. Во всех вариантах нужны лимиты буфера, восстановление соединения и правила повторов/потери событий.

8.9 · Что проверить перед демонстрацией API

Проверяй не только счастливый путь

Тесты: валидный запрос, неверный тип, отсутствующий ресурс, чужой объект, одновременное обновление, повтор после таймаута, превышение лимита, рестарт. Изолируй состояние тестов; отдельно проверь бизнес-логику и полный HTTP-путь.

Объясняй границы учебного проекта честно

Назови место хранения, число процессов, механизм синхронизации, лимиты и известные отказы. Метрики latency/error rate, корреляция запросов и health endpoints помогают искать сбои, но не заменяют долговечность и корректный контракт.

0. Сначала реши: программа вообще корректна?

Не вычисляй вывод до проверки компиляции и UB

Проверь access control, deleted/ambiguous overload, abstract type, missing virtual destructor при полиморфном delete, dangling reference, use-after-move по контракту типа, unsequenced operations и data race. Если код ill-formed или имеет UB, единственного гарантированного вывода нет.

1. Нарисуй объект как дерево подобъектов

Construction order не определяется initializer list

Сначала virtual bases (самым derived объектом), затем direct bases слева направо, затем non-static fields в порядке объявления, затем тело конструктора. Destruction идёт строго обратно. Для каждого полностью созданного подобъекта сразу запиши соответствующий destructor.

Delegating constructor выполняет target constructor, затем своё тело

Если target завершился исключением, делегирующее тело не запускается. Function-try-block конструктора видит ошибку, но после выхода из handler исключение автоматически перебрасывается.

2. Раздели storage и lifetime

new-expression: allocate → construct; delete-expression: destroy → deallocate

E* p = new E; // если E::E бросил, подходящий operator delete
              // освобождает storage; p не получает значение
delete p;       // при успехе: ~E(), затем deallocation

Если конструктор полного объекта бросил

Деструктор самого полного объекта не вызывается. Уже построенные поля и базы уничтожаются в обратном порядке. Для автоматического объекта ничего больше делать не нужно; при new-expression storage освобождается автоматически подходящей deallocation function.

3. Для каждого вызова отдели static type от dynamic type

Virtual body выбирается по final overrider, но не всё виртуально

Default arguments связываются по static type; non-virtual overload/name lookup — тоже compile-time. В constructor/destructor virtual dispatch не уходит в более-derived часть. Передача по значению может сделать slicing.

4. Пройди исключительный и обычный пути отдельно

Таблица трассировки

ШАГ | СОБЫТИЕ                    | ЖИВЫЕ ОБЪЕКТЫ
1   | B::B                         | B
2   | member::member               | B, member
3   | D::D throws                  | B, member
4   | member::~member, B::~B       | —
5   | matching catch               | —

Не смешивай три варианта одной задачи

Автоматический объект + throw, успешный new/delete и new с исключением конструктора имеют разные точки cleanup. Выпиши trace для каждого варианта заново, затем сравни.

Фраза хорошего ответа

Сначала контракт, затем вывод

«Код корректен/некорректен потому что … . При корректном пути порядок задают … . Вот состояние после каждого шага … . При альтернативе с исключением уничтожаются только … . Поэтому гарантированный вывод такой: …». Это сильнее угадывания строк по памяти.

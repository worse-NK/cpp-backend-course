Сначала — карта

Не арендуем сервер и не открываем порты. Сначала договоримся о маршруте, инструментах и границах учебного проекта.

Что получится в конце

Сервер — слово с двумя значениями. Серверная программа принимает запросы и выдаёт ответы. Серверная машина — компьютер, на котором эта программа работает. Сначала обе стороны будут на твоём компьютере: curl выступит клиентом, а собранный C++-процесс — сервером. Позже программу перенесём на другую машину. Никакой особой «серверной версии C++» для этого не нужно.

Проект называется course_tasks. Он хранит задачи с полями id, title, done и version. Мы не будем переписывать сервер после каждого этапа: один интерфейс хранилища имеет реализацию в памяти и реализацию для PostgreSQL. Так можно увидеть, где HTTP-контракт не зависит от места хранения, а где появляются новые отказы.

Что происходит внутри: необязательный маршрут по архитектуре

Сначала можно выполнить команды и сверить результаты. Когда захочешь объяснить не только «работает», но и почему система ведёт себя именно так, возвращайся к этим разборам по мере прохождения соответствующих станций:

  • От сетевых данных до обработчика: где работают ядро и программа и почему видимый пакет ещё не означает исполненный запрос.
  • Модуль, процесс и сетевой сервис: какие границы можно разделить без обязательного усложнения приложения.
  • От изменения строки до восстановления: чем различаются изменение в памяти базы, фиксация и сохранность после сбоя.
  • Полное время запроса: как найти ожидание между поступлением данных, началом обработчика и выполнением SQL.

Это объяснения к наблюдениям практикума, не дополнительные инструменты, которые нужно установить до первого запуска. Нереализованные расширения в теории явно отделены от возможностей нашего проекта.

Среда, для которой написаны команды

Основной маршрут рассчитан на Ubuntu 24.04 LTS, Linux x86-64 и обычный пользовательский аккаунт. Подойдёт отдельная VM (виртуальная машина — другая ОС, запущенная внутри твоего компьютера). В Windows можно использовать Ubuntu в WSL2 для локальных шагов. Перенос на отдельную VM всё равно полезен: он не даст случайно принять второй терминал той же ОС за другую машину. Нативные команды PowerShell и macOS здесь не обещаются.

Для сборки нужны компилятор с C++20, CMake не ниже 3.24, Python 3.10+ и curl. Первый запуск скачивает закреплённые библиотеки по HTTPS. Для контейнерного этапа нужны настроенный Docker Engine и Compose v2. Используй поддерживаемую актуальную версию Engine не ниже 28: у старых версий были особенности доступности опубликованных на loopback портов. Практический ориентир для учебной VM — 2 виртуальных CPU, 4 ГБ RAM и не менее 10 ГБ свободного диска; это запас для сборки, не требование самого API.

Локальная Ubuntu · только если этих инструментов ещё нет
sudo apt update
sudo apt install build-essential cmake python3 curl git ca-certificates

sudo выполняет установку с правами администратора. На рабочей машине сначала согласуй установку с её владельцем. Docker устанавливай по официальной инструкции для Ubuntu, а не случайным скриптом из статьи. Доступ к Docker daemon практически равен административному доступу к машине; не добавляй себя в группу docker, считая это безобидным разрешением.

Локальная Ubuntu · проверка инструментов
g++ --version
cmake --version
python3 --version
curl --version
git --version

Для следующего этапа будет ещё docker compose version. Если написано command not found, исправь установку соответствующего инструмента. Не продолжай копировать команды в надежде, что отсутствие зависимости «само пройдёт».

Правило подписи команд

У каждого блока указан компьютер и, где нужно, терминал. Локальный компьютер — место, с которого ты управляешь практикумом. Linux-VM/VPS — другая машина, куда входишь по SSH. Команда docker compose exec db … запускается в терминале хоста, но её последняя часть выполняется внутри контейнера db. Никакие команды со страницы не исполняются браузером.

Связка && между командами означает «выполни следующую только при успешном завершении предыдущей». Это защита от продолжения в неправильном каталоге или перезаписи после неудачной подготовки. Если блок остановился с ошибкой, разбирай её, а не убирай связку. Проверочные запросы с намеренно ошибочными статусами показываются отдельно.

Пока всё доступно только локально. Не заменяй 127.0.0.1 на 0.0.0.0 в надежде «починить сеть». Не открывай 8080 или 5432 в роутере и облачном firewall (фильтре сетевых соединений). Публичный доступ разбирается отдельно, после проверок.

Граница учебного проекта

Здесь есть проверка JSON, случайный Bearer-токен (секрет, предъявление которого даёт доступ), лимит тела запроса и условные изменения по версии. Но один общий токен — не полноценная система пользователей и прав. Лимит очереди и таймауты — не исчерпывающая защита от перегрузки. PostgreSQL-реализация открывает соединение на операцию, а не демонстрирует промышленный пул соединений. Не размещай личные данные, реальные пароли пользователей и рабочую информацию в этом сервисе.

Позже полезно будет заменить общий токен личностями и разрешениями, добавить миграции схемы, пул, метрики и отдельное управление секретами. Сначала нужно уверенно пройти базовый путь запроса и уметь объяснить каждое соединение. Сам факт аренды VPS не превращает учебный проект в промышленный.

Что действительно проверено в этом примере

25 октября 2026 проверены сборка и тесты C++20, реальные HTTP-запросы к нативному процессу и контейнерному приложению с PostgreSQL 18, ошибки входа, одновременные изменения, лимит задач, остановка, перезапуски, отказ базы и восстановление данных из логической копии. Caddyfile проверен настоящим caddy validate в изолированном контейнере. Инструкции SSH и публичного размещения сверены с документацией, но развёртывание на отдельной пользовательской VM/VPS, реальный DNS и получение публичного сертификата в эту проверку не входили. Особенности твоего гипервизора, сети и провайдера нужно проверить отдельно.

Перед следующим шагом

  • Понимаешь разницу между программой и машиной-сервером.
  • Есть Linux-окружение и инструменты; работа не требует root-запуска приложения.
  • Понимаешь, что сначала никто из интернета к API подключаться не должен.

Запускаем локально

Соберём настоящий HTTP-сервис, запустим его в одном терминале и обратимся к нему из другого.

1. Получаем исходники, не секреты

Открой терминал в каталоге, где можно создать новый учебный проект. Следующая команда создаст папку cpp-course. Если папка уже существует, выбери другое имя или используй свою ранее скачанную копию — не удаляй её наугад.

Локальный компьютер · новый каталог для курса
git clone --depth 1 https://github.com/worse-NK/cpp-backend-course.git cpp-course &&
cd cpp-course/roadmap/examples/service-workshop &&
pwd

Последняя команда показывает текущий каталог. Его конец должен быть /roadmap/examples/service-workshop. Далее все локальные команды выполняются отсюда, если явно не указано другое. Если Git не нужен, можно скачать ZIP репозитория и открыть эту же вложенную папку после распаковки.

ФайлЗа что отвечает

2. Создаём свои секреты

Локальный компьютер · каталог service-workshop
python3 lab.py init &&
python3 lab.py check-env

init один раз создаёт .env с тремя независимыми случайными секретами и .secrets/client.curl с заголовком авторизации для клиента. Каждый секрет содержит 64 шестнадцатеричных символа. Файлы доступны только владельцу (режим 0600), каталог .secrets — только владельцу на чтение, запись и проход (0700). Помощник не печатает значения и не заменяет существующие файлы.

Ожидаемая проверка наличия, без значений

APP_TOKEN: present
POSTGRES_PASSWORD: present
APP_DB_PASSWORD: present

Для локального режима пока нужен только APP_TOKEN. Два других значения понадобятся базе: администратору PostgreSQL и отдельной роли приложения. Они не должны совпадать. Не отправляй .env и client.curl в Git, чат или скриншот. Не выполняй source .env: помощник сам читает только известные имена и проверяет формат, не исполняя содержимое как shell-код.

Если init пишет, что файл уже существует

Это защита от случайной смены токена и паролей. Если ты уже выполнял шаг в этой копии, продолжай с check-env. Не удаляй файл ради повторного запуска: при существующей PostgreSQL смена текста в .env не меняет пароль внутри базы. Для независимого эксперимента создай отдельную копию проекта.

3. Собираем и проверяем

Локальный компьютер · каталог service-workshop
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug &&
cmake --build build --parallel 2 &&
ctest --test-dir build --output-on-failure

Первая команда читает проект из текущего каталога (-S .) и создаёт отдельный каталог сборки build. Она скачивает cpp-httplib 0.59.0 и nlohmann/json 3.12.0: версии и SHA-256 архивов закреплены в CMake, чтобы другой архив не был молча принят. Вторая компилирует программу двумя параллельными заданиями. Третья запускает тесты. Итог сборки — build/course_tasks. Отключённая опция COURSE_WITH_POSTGRES означает, что сейчас не требуются заголовки libpq и работающая база.

Если загрузка зависимости не удалась, проверь интернет, прокси и доверенные сертификаты. Не отключай проверку TLS или контроль хеша, чтобы «продавить» сборку. Ошибка компилятора — другой класс сбоя: сохрани первую содержательную ошибку, версии инструментов и точную команду. Предупреждения перед ней не всегда являются причиной.

4. Запускаем процесс

Локальный компьютер · терминал A · оставить работающим
python3 lab.py run

Помощник запускает собранный бинарник, передаёт токен и принудительно выбирает хранилище в памяти и 127.0.0.1:8080. Терминал не возвращает приглашение, пока процесс работает. Это нормальное поведение: мы не запускали фоновую службу.

Локальный компьютер · терминал B · тот же каталог проекта
curl --noproxy 127.0.0.1 --connect-timeout 2 --max-time 5 -i http://127.0.0.1:8080/health/ready
curl --config .secrets/client.curl -i http://127.0.0.1:8080/tasks

Первый ответ должен иметь статус 200. Второй — 200 и пустой JSON-массив [], если процесс ещё не получал задач. -i добавляет заголовки ответа к выводу. Конфиг клиента добавляет Bearer-токен, ограничение соединения двумя секундами и всего запроса пятью секундами. Не включай -v или трассировку curl: они могут показать секретный заголовок запроса.

Если нужен другой порт, останови процесс Ctrl-C в терминале A, запусти python3 lab.py run --port 18080 и замени порт во всех локальных URL. Не пытайся устранить конфликт командой, завершающей все процессы с похожим именем.

Под капотом: кто исполняет запрос и где он может ждать

В этом проекте четыре рабочих потока и очередь до 32 заданий обслуживания соединений. Это не «32 пользователя»: одно соединение может нести несколько запросов, а до вызова обработчика есть отдельные места ожидания. В разборе реального пути запроса показаны именно эти настройки, удержание потока во время ожидания и причина, по которой даже лёгкая health-проверка не всегда ответит немедленно. Для первого запуска знать внутренний код библиотеки наизусть не требуется.

Результат этапа

Ты запустил собственный HTTP-сервер. Пока «собственный» означает собранный и управляемый тобой процесс, а не обязательно написанную с нуля реализацию TCP и HTTP.

Перед переходом убедись: объясняешь, почему нужны два терминала, что занимает порт и почему другой компьютер не достигает сервиса по твоему 127.0.0.1.

ПРАКТИКУМ · ШАГ 3 ИЗ 7

Работаем с API

Создадим задачу, прочитаем ответ и проследим, как сервер защищает изменение от устаревшей версии.

1. Создание — это запрос и наблюдаемый результат

Сервер из предыдущего шага должен работать. Команды выполняй во втором терминале, из каталога проекта. Сначала убедимся, что защита действительно включена:

Локальный компьютер · терминал B · намеренно без токена
curl --noproxy 127.0.0.1 --connect-timeout 2 --max-time 5 -i http://127.0.0.1:8080/tasks

Ожидается 401. Это не «сервис сломан»: клиент не предъявил право доступа. Дальше конфиг клиента будет добавлять токен. Не вводим токен вручную в команду, чтобы не сохранять его в истории shell.

Локальный компьютер · терминал B · создать задачу
curl --config .secrets/client.curl -i \
  -H 'Content-Type: application/json' \
  --data '{"title":"Understand one HTTP request","done":false}' \
  http://127.0.0.1:8080/tasks

Обратная косая черта в конце строки продолжает одну shell-команду. После неё не должно быть пробелов. --data без явного метода выбирает POST. Заголовок Content-Type говорит серверу, что тело содержит JSON, а не форму.

Существенная часть ответа на первое создание в пустом хранилище

HTTP/1.1 201 Created
Location: /tasks/1
ETag: "v1"

{"done":false,"id":1,"title":"Understand one HTTP request","version":1}

Порядок заголовков и JSON-полей не важен. 201 сообщает о создании; Location указывает ресурс; ETag — метку этой версии представления. Идентификатор назначает сервер. Если ты уже создавал задачи, ID не обязан быть 1. Далее подставь фактический ID из своего ответа:

Локальный компьютер · терминал B · заменить 1 при необходимости
TASK_ID=1
curl --config .secrets/client.curl -i "http://127.0.0.1:8080/tasks/$TASK_ID"
curl --config .secrets/client.curl -i http://127.0.0.1:8080/tasks

TASK_ID — переменная текущего shell, а не настройка сервера. Двойные кавычки позволяют подставить её в URL. GET одной задачи возвращает объект и его ETag; GET списка — массив по возрастанию ID. В учебной реализации не более 1000 задач: это явная граница, а не обещание бесконечной выдачи.

2. Обновление: почему нужен If-Match

Представь двух клиентов, прочитавших версию 1. Первый отметил задачу выполненной. Второй всё ещё видит старую копию и меняет заголовок. Без проверки версии второй может незаметно вернуть done:false. Условное изменение означает: «запиши это только если текущая метка всё ещё та, которую я прочитал».

Локальный компьютер · терминал B · обновление прочитанной v1
curl --config .secrets/client.curl -i -X PUT \
  -H 'Content-Type: application/json' \
  -H 'If-Match: "v1"' \
  --data '{"title":"Understand one HTTP request","done":true}' \
  "http://127.0.0.1:8080/tasks/$TASK_ID"

Если задача всё ещё имеет версию 1, получишь 200, done:true и version:2. В этом PUT-ответе нет ETag: сервер преобразует переданное представление, добавляя управляемые им поля. По правилу HTTP нельзя выдавать validator (метку для последующей проверки версии) как будто принятые данные сохранены без преобразования. Чтобы получить актуальное представление и его ETag: "v2", выполни отдельный GET:

Локальный компьютер · терминал B · прочитать состояние после PUT
curl --config .secrets/client.curl -i "http://127.0.0.1:8080/tasks/$TASK_ID"

Теперь повтори ровно прежнюю PUT-команду с If-Match: "v1". Ожидается 412 Precondition Failed: условие уже ложно. Повтор не должен незаметно перезаписать новую версию. Предварительное условие защищает момент изменения, а не резервирует ресурс навсегда: после GET другой клиент снова может изменить задачу, и следующий PUT тогда тоже получит 412.

Наш API намеренно принимает только одну сильную метку вида "vN", где N — положительное десятичное число без ведущих нулей в диапазоне signed 64-bit. Списки меток, * и слабые метки W/… здесь не реализованы. Это учебное подмножество, не полный синтаксис HTTP If-Match. Сервер возвращает 428, когда условие отсутствует, 400 — когда этот поддерживаемый формат нарушен, 412 — когда подходящей текущей версии нет.

Граница простой метки vN. Она подходит только для неизменной схемы представления и непрерывной истории идентификатора/версии. Нативный memory-режим при перезапуске теряет всю историю, поэтому старые ID и метки надо отбросить: он не обещает защиту старого клиента после повторного создания хранилища. Для многопроцессного и долговечного API нужна согласованная политика идентификаторов и валидаторов, учитывающая восстановление данных и изменение представления. Одна локальная переменная version этого не обеспечивает.

Что делать клиенту после 412?

Сначала заново прочитать задачу. Потом решить, как совместить своё намерение с новым состоянием, и только после этого отправить изменение с актуальным ETag. Слепое повторение со «свежей меткой любой ценой» убирает смысл защиты. После сетевого таймаута тоже нельзя автоматически считать, что запись не произошла: проверь наблюдаемое состояние.

3. Различаем ошибки входа

Для POST и PUT разрешены ровно два поля: непустой UTF-8 заголовок title длиной до 200 байт без нулевого символа и булево done. Кириллическая буква обычно занимает больше байта; лимит в байтах — не обещание 200 любых символов. ID и версию нельзя назначить из тела.

Локальный компьютер · терминал B · намеренно неправильный тип
curl --config .secrets/client.curl -i \
  -H 'Content-Type: application/json' \
  --data '{"title":"Wrong type","done":"false"}' \
  http://127.0.0.1:8080/tasks

Ожидается 422: JSON корректен синтаксически, но строка "false" — не булево значение false. Из-за fail-with-body в конфиге curl завершится с ненулевым кодом и всё равно покажет ответ. Для намеренных ошибок это ожидаемо.

Измени запросОжидаемый статусЧто именно проверили

4. Удаление и потеря памяти процесса

Локальный компьютер · терминал B · после успешного PUT до v2
curl --config .secrets/client.curl -i -X DELETE \
  -H 'If-Match: "v2"' "http://127.0.0.1:8080/tasks/$TASK_ID"
curl --config .secrets/client.curl -i "http://127.0.0.1:8080/tasks/$TASK_ID"

DELETE с текущей меткой возвращает 204 без тела; последующий GET — 404. Если ты делал дополнительные изменения, сначала прочитай настоящий ETag. Повтор DELETE с прежней меткой вернёт 412, потому что текущего представления уже нет. Идемпотентность метода не требует одинакового статуса каждого повтора.

Снова создай одну задачу. В терминале A нажми Ctrl-C, дождись завершения и запусти python3 lab.py run. GET списка покажет []. Это не ошибка базы: её ещё нет. Все данные принадлежали памяти завершившегося процесса. Перед следующим этапом останови нативный процесс, чтобы освободить порт 8080.

Проверь себя без подсказки

  1. Почему 401 доказывает больше о доступности сервера, чем Connection refused?
  2. Почему повтор старого PUT даёт 412, а не ещё одно успешное изменение?
  3. Где были задачи и почему перезапуск их потерял?

Сохрани свои команды и обезличенные статусы в заметку. Токен и заголовок Authorization в неё не входят.

Добавляем PostgreSQL

Контракт API остаётся прежним. Меняются место хранения и способ запуска: вместо одного процесса — приложение и база в разных контейнерах.

1. Что меняется, а что остаётся прежним

POST, GET, PUT и DELETE остаются теми же. Но завершение процесса больше не должно уничтожать задачи: теперь они записаны в PostgreSQL. Контейнер — изолированное окружение процесса, а не отдельный физический компьютер. Образ содержит файлы для его запуска. Volume — отдельное хранилище Docker, которое не исчезает при замене контейнера.

Файл compose.yaml описывает два сервиса: app и db. Compose создаёт их вместе с сетями и хранилищем. Образ приложения собирается из нашего Dockerfile; образ PostgreSQL 18 берётся из официального репозитория. Версии C++-библиотек закреплены архивами и хешами; теги базовых образов могут получать обновления. Для строгой воспроизводимости релиза дополнительно закрепляют digest образа (хеш его содержимого), но не отказываются из-за этого от обновлений безопасности.

Почему приложение внутри контейнера слушает 0.0.0.0, хотя раньше мы это запрещали менять наугад? Этот адрес означает «все IPv4-интерфейсы данного окружения». Привязка к контейнерному 127.0.0.1 не принимала бы перенаправленные снаружи контейнера соединения. Видимость на машине-хосте задаётся отдельно: 127.0.0.1:8080:8080. Слева — адрес и порт хоста, справа — порт контейнера. Если удалить адрес слева, можно случайно опубликовать порт на внешних интерфейсах.

2. Запускаем, не раскрывая настройки

До первого запуска проверь цель. У проекта фиксированное имя course-service-workshop. Две папки с этим именем на одном Docker daemon не являются независимыми стендами. Если такой проект у тебя уже есть, остановись и не заменяй его другой копией. Выполни docker context show: Docker должен управлять именно выбранным учебным хостом, а не рабочим или неожиданно удалённым сервером. Контекст с названием default тоже стоит сверить со своей настройкой; переменные DOCKER_HOST/DOCKER_CONTEXT не должны незаметно менять цель.

Нативный процесс из предыдущего шага должен быть остановлен. Docker уже должен быть настроен. Команда docker version должна показывать и клиента, и сервер, а docker compose version — Compose v2. При ошибке доступа к daemon следуй инструкции администратора; не меняй права сокета на 666 и не публикуй Docker API в сеть.

Локальный компьютер · каталог service-workshop
unset APP_TOKEN POSTGRES_PASSWORD APP_DB_PASSWORD
python3 lab.py check-env &&
docker compose config --quiet &&
docker compose up --build -d --wait --wait-timeout 240 &&
docker compose ps

unset убирает только три переменные из текущего терминала. Это важно: экспортированное значение из shell может переопределить одноимённую запись .env, а check-env проверяет именно файл. Секреты в файле сохраняются. config --quiet проверяет конфигурацию, не печатая подставленные значения. Не убирай --quiet при отправке результата проверки в чат.

--build собирает образ, -d запускает контейнеры в фоне, --wait ждёт их готовности. Первая сборка может занять несколько минут; сборка ещё не является HTTP-запросом. После неё app и db должны стать healthy. Если ожидание истекло, команда завершится ошибкой, но контейнеры могут остаться запущенными — проверь состояние, а не запускай новые копии вслепую.

Локальный компьютер · диагностика, без вывода секретов
docker compose logs --tail 40 app
docker compose logs --tail 40 db
docker compose port app 8080
curl --noproxy 127.0.0.1 --connect-timeout 2 --max-time 5 -i http://127.0.0.1:8080/health/ready
curl --config .secrets/client.curl -i http://127.0.0.1:8080/tasks

Публикация должна показывать 127.0.0.1:8080, не 0.0.0.0:8080. При первом запуске список задач пустой: прежние задачи жили в памяти другого процесса, автоматического переноса не было. Сообщения приложения содержат шаблон маршрута и статус, но не токен, тело запроса и пароль базы. Всё равно просматривай диагностический вывод перед публикацией: сторонние инструменты могут писать больше, чем наше приложение.

3. Проверяем сохранность, а не наличие контейнера

Создай задачу командами из шага «Работаем с API», например с заголовком Survives restart. Запиши её ID. Затем:

Локальный компьютер · перезапуск только своего приложения
docker compose restart app &&
docker compose up -d --wait --wait-timeout 90 &&
curl --config .secrets/client.curl -i http://127.0.0.1:8080/tasks

Задача должна остаться. Теперь остановим весь проект и создадим контейнеры заново, сохранив volume:

Локальный компьютер · тот же проект и каталог
docker compose down &&
docker compose up -d --wait --wait-timeout 90 &&
curl --config .secrets/client.curl -i http://127.0.0.1:8080/tasks

Задача снова должна быть в ответе. down удаляет контейнеры и сети проекта, но по умолчанию сохраняет именованный volume. Мы не добавляем -v: эта опция удалила бы данные. Также не используем общие команды prune, затрагивающие другие проекты.

У Compose задано имя course-service-workshop. Все команды здесь должны относиться к одной копии проекта и одному Docker daemon. Две папки с тем же именем проекта не являются двумя независимыми стендами. Если Docker CLI настроен на удалённый context, контейнеры запускаются на его машине, а 127.0.0.1 клиента остаётся твоим: до дальнейшего выполнения выбери нужный локальный context по документации Docker.

Опыт подтвердил конкретное свойство: данные пережили замену контейнеров при сохранённом volume. Это ещё не проверка потери диска или сохранности после любого сбоя. Как одна запись проходит через SQL, COMMIT и восстановление, разбирается в «От UPDATE до восстановления». Там же объясняется, почему успешный ответ API и надёжность его хранилища должны иметь согласованную границу.

4. Кто имеет право работать с базой

Первичная инициализация выполняется администратором PostgreSQL и создаёт таблицу public.tasks. Сам API подключается под отдельной ролью course_app: ей разрешены чтение, вставка, изменение, удаление задач и использование sequence (генератора последовательных ID). Ей не выданы права создавать роли или базы. Параметры запросов передаются отдельно от SQL-текста.

Локальный компьютер · SQL выполнится внутри db
docker compose exec -T db psql -U postgres -d course_tasks \
  -v ON_ERROR_STOP=1 -c 'SELECT id, title, done, version FROM public.tasks ORDER BY id;'

Это административное учебное наблюдение через локальный сокет контейнера, не соединение приложения. В промышленной системе доступ к daemon и административной роли контролируется отдельно. Environment-секреты контейнера может прочитать владелец Docker daemon/root; режим 0600 защищает файл от обычных соседних пользователей, но не от администратора.

Инициализация не повторяется при каждом старте. Скрипт из docker-entrypoint-initdb.d выполняется только для нового пустого хранилища PostgreSQL. Правка schema.sql не обновляет работающую таблицу, а смена APP_DB_PASSWORD в файле не меняет пароль уже созданной роли. Для существующей базы нужны миграция и согласованная смена учётных данных. Не «лечи» это удалением volume с нужными данными.

Для PostgreSQL 18 volume в примере смонтирован в /var/lib/postgresql, а не в путь из старых статей про PostgreSQL 17. У приложения есть ограничение времени соединения и SQL-операции; при отказе базы клиент получает общий 503, а не строку подключения. Перезапуск по restart: unless-stopped относится к завершению контейнера, а unhealthy сам по себе не заставляет обычный Compose автоматически его перезапустить.

Если добавлять копии, кэш или уведомления — что изменится

В текущем проекте одна база и один app; кэш, реплика базы и доставка событий не включены. После основного опыта можно разобрать три независимых расширения, не устанавливая их одновременно:

  • Два экземпляра API: общая база задач ещё не объединяет локальные сессии, ключи повторов и открытые соединения.
  • Копия базы на другой машине: почему подтверждённое изменение ещё не обязательно видно при чтении с реплики.
  • Кэш перед базой: как устаревшая задача может вернуться в кэш даже после удаления ключа.
  • Изменение задачи и внешнее уведомление: почему нужен отдельный договор между фиксацией данных и доставкой события.

Это продолжение станции 9B, а не скрытые требования к работоспособности нашего простого Compose-проекта. Сначала научись объяснять уже полученные результаты и сохранённые данные.

Переносим на Linux-VM

Теперь сервер работает не в том же окружении, где находится клиент. Учимся различать адреса машин, их localhost и назначение SSH-туннеля.

1. Какая VM нужна

Нужна отдельная Ubuntu 24.04 LTS, которой ты управляешь: например, VM в VirtualBox, VMware, UTM или другом гипервизоре. Создай обычного пользователя и снимок чистого состояния (snapshot — сохранённое состояние VM, к которому можно вернуться). Для удалённого входа внутри гостевой ОС должен работать OpenSSH Server. Docker Engine, Compose v2, Python 3 и curl настраиваются внутри этой VM. Компилятор на хосте VM не заменяет компилятор внутри образа; Dockerfile принесёт инструменты сборки сам.

Способ сетевого подключения зависит от гипервизора. В NAT-режиме может понадобиться его перенаправление SSH-порта; в host-only или bridged у VM может быть собственный доступный адрес. Не меняй режимы наугад. Сначала добейся простого входа по SSH по инструкции своего гипервизора и узнай IP гостя через его консоль. Для практики не требуется пробрасывать HTTP 8080 наружу.

Для скачивания пакетов и образов VM также нужен исходящий интернет. Один только host-only адаптер обычно даёт связь с хостом, но не выход в интернет; часто к нему добавляют второй адаптер NAT. Другой вариант — один NAT-адаптер и перенаправление только SSH с loopback хоста, например 127.0.0.1:2222 → VM:22. Тогда SSH-клиент использует адрес 127.0.0.1 и порт 2222, а не внутренний IP гостя. Эти настройки относятся к гипервизору, не к Compose.

Если SSH-сервер не был установлен вместе с Ubuntu, подготовь его через консоль самой VM (окно гостевой ОС, ещё не SSH). Команды ниже устанавливают службу, позволяют ей запускаться при загрузке и показывают её состояние. Выполняй их только в своей учебной VM:

Linux-VM · её консоль в гипервизоре · ещё до первого SSH-входа
sudo apt update &&
sudo apt install openssh-server python3 curl ca-certificates &&
sudo systemctl enable --now ssh
systemctl --no-pager status ssh
ip -br address
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Ожидай активную службу (либо активную socket-активацию в конфигурациях Ubuntu), адрес нужного сетевого интерфейса и отпечаток публичного Ed25519-ключа. Последняя команда читает файл с окончанием .pub, не приватный ключ. Сравнивай его с приглашением клиента именно для этого алгоритма. Если интерфейс не получил адрес или SSH недоступен, исправь подключение VM; не отключай проверку ключа и firewall вслепую. Docker установи отдельно по ссылке из первого шага, внутри гостевой Ubuntu.

Рабочий сервер организации для этого не подходит. Не устанавливай Docker и не запускай Compose на машине, которой не имеешь права управлять. Основной маршрут предназначен для отдельной учебной VM. Оставь доступ к её консоли, чтобы ошибка SSH не отрезала управление.

2. Первый SSH-вход: пользователь и адрес — разные вещи

В записи learner@192.168.56.101 слева имя пользователя на удалённой машине, справа адрес машины, а не имя твоего локального аккаунта. Адрес из частной сети работает только там, откуда к ней есть маршрут; он не становится доступным всему миру. Чтобы не повторять пользователя, адрес и нестандартный порт во всех ssh/scp-командах, зададим одно короткое имя — course-vm.

На локальном компьютере открой в редакторе ~/.ssh/config (при необходимости создай каталог .ssh и файл). Добавь следующую отдельную запись, не заменяя существующие настройки. Это текст конфигурации, не команды терминала. Замени имя пользователя и адрес на свои:

Host course-vm
    HostName 192.168.56.101
    User learner
    Port 22

Для варианта NAT с перенаправлением 127.0.0.1:2222 → VM:22 в этой записи укажи HostName 127.0.0.1 и Port 2222. Имя course-vm — локальный псевдоним SSH, а не DNS-запись в интернете. Дальнейшие команды одинаковы для обоих способов подключения.

Локальный компьютер · после настройки записи course-vm
VM_HOST=course-vm
ssh "$VM_HOST"

При первом входе SSH показывает fingerprint (краткий отпечаток) ключа сервера. Сверь его через доверенную консоль VM, а не просто отвечай yes привычным движением. Это позволяет отличить нужную машину от подмены. При неожиданной смене ключа сначала выясни причину, а не отключай проверку или удаляй запись автоматически. Ключ сервера и твой пользовательский SSH-ключ решают разные задачи: первый удостоверяет машину, второй может удостоверять тебя.

Linux-VM · после SSH-входа
hostname
whoami
pwd
python3 --version
docker version
docker compose version
exit

После exit снова работаешь в локальном терминале. Если непонятно, где сейчас выполняется команда, остановись и проверь hostname. Не продолжай перенос, пока обычный вход и работа Docker в VM не проверены. И ssh, и scp читают запись course-vm, поэтому нестандартный порт не нужно дописывать в каждой строке. Без такой записи у ssh порт задавался бы через -p, а у scp — через -P; это разные опции.

3. Переносим только исходники

Локальный компьютер · каталог service-workshop
python3 lab.py pack &&
ssh "$VM_HOST" 'mkdir -m 700 course-workshop-upload' &&
scp service-workshop-source.tar.gz "$VM_HOST:course-workshop-upload/"

Архив создаётся по явному списку: C++-исходники, CMake, Dockerfile и конфигурации. В нём нет .env, клиентского токена, SSH-ключей, каталога build или всей истории Git. Помощник откажется заменить существующий архив. Если папка загрузки на VM уже существует, не продолжай слепо: используй новый явно выбранный каталог для нового эксперимента или проверь содержимое старого.

Локальный компьютер · открыть отдельный SSH-сеанс
ssh "$VM_HOST"
Linux-VM · в SSH-сеансе
cd course-workshop-upload &&
tar -tzf service-workshop-source.tar.gz &&
tar -xzf service-workshop-source.tar.gz &&
cd service-workshop &&
python3 lab.py init &&
python3 lab.py check-env &&
unset APP_TOKEN POSTGRES_PASSWORD APP_DB_PASSWORD &&
docker compose config --quiet &&
docker compose up --build -d --wait --wait-timeout 240 &&
docker compose port app 8080 &&
curl --config .secrets/client.curl -i http://127.0.0.1:8080/tasks

Распаковываем свой архив в новый учебный каталог; произвольные чужие tar-архивы могут быть опасны. Секреты создаются заново на VM, поэтому локальный токен не подойдёт удалённому API. Публикация app и здесь должна быть 127.0.0.1:8080. Последний curl выполняется внутри VM, так что обращается к её loopback. Это пока не проверка доступа с твоего компьютера.

4. Строим SSH-туннель и прослеживаем адреса

Оставь SSH-сеанс управления открытым. В новом локальном терминале задай тот же VM_HOST и запусти туннель:

Локальный компьютер · отдельный терминал для туннеля
VM_HOST=course-vm
ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18080:127.0.0.1:8080 "$VM_HOST"

-N не запускает удалённую команду. В -L первые адрес и порт относятся к локальному слушателю; последние — к соединению, которое SSH-сервер откроет на удалённой стороне. ExitOnForwardFailure не даёт молча продолжить, если локальный порт занят. Но он не гарантирует, что приложение по ту сторону живо: это проверит запрос. Терминал остаётся занят туннелем до Ctrl-C. Обрыв туннеля не останавливает удалённые контейнеры.

Локальный компьютер · другой терминал · безопасная проверка без токена
curl --noproxy 127.0.0.1 --connect-timeout 2 --max-time 5 -i \
  http://127.0.0.1:18080/health/ready

Ожидается 200. При Connection refused проверь, жив ли локальный SSH-процесс и слушает ли 18080. Если SSH пишет connect failed, проверь приложение на самой VM. Если локальный 18080 уже занят, выбери другой и замени URL клиента. Не меняй локальную привязку туннеля на 0.0.0.0 — это сделало бы его доступным соседним компьютерам.

5. Авторизуем клиент именно для этой VM

Нужен токен удалённого проекта, но его не следует печатать или копировать через чат. Передадим готовый curl-конфиг по SSH. Следующий блок создаёт новый приватный локальный каталог. Если он уже существует, остановись: не заменяй старые учётные данные наугад.

Локальный компьютер · каталог service-workshop · VM_HOST задан в этом терминале
mkdir -m 700 .secrets-vm &&
scp "$VM_HOST:course-workshop-upload/service-workshop/.secrets/client.curl" .secrets-vm/client.curl &&
chmod 600 .secrets-vm/client.curl &&
curl --config .secrets-vm/client.curl -i http://127.0.0.1:18080/tasks

Каталог 0700 закрывает доступ соседним пользователям уже во время передачи; режим файла затем явно ограничивается. Не добавляй этот каталог в Git: он начинается с .secrets и исключён правилами проекта. Не передавай приватный SSH-ключ на VM — он остаётся на клиенте. Измени и прочитай задачу через туннель; затем в SSH-сеансе на VM прочитай список напрямую по 8080. Оба клиента должны видеть одни данные.

Результат этапа

  • Один сервис работает в отдельной VM; локальный нативный процесс для него не нужен.
  • На своей машине обращаешься к 18080, на VM — к 8080.
  • Токен создан на VM, передан клиенту по SSH и не попал в архив исходников.
  • Закрытие туннеля убирает доступ через него, но не останавливает сервер.

Необязательно: VPS и HTTPS

Тот же проект можно запустить на арендованной Linux-машине. Публичный доступ — отдельное осознанное действие, а не побочный эффект запуска.

Этот шаг необязателен. Основной практикум уже дал настоящий удалённый запуск в VM. VPS полезен, если хочешь увидеть публичный адрес, DNS, сертификат и ответственность за доступный из интернета сервис. Аренда и домен могут стоить денег; обещание бесплатного бессрочного сервера здесь не даётся.

1. VPS не меняет смысл команд

VPS (виртуальный выделенный сервер) — Linux-машина у провайдера. Ты получаешь доступ по SSH и управляешь процессами почти так же, как в своей VM, но машина обычно имеет публичный IP и постоянно встречает посторонние попытки подключения. Считай её отдельным окружением: новые секреты, свой volume и свой каталог проекта.

Выбирай небольшой Linux-сервер с ресурсами не меньше учебной VM и понятным способом удаления. До оплаты проверь стоимость диска, публичного IP, трафика и резервных копий: выключенная машина не обязательно перестаёт оплачиваться. Убедись, что есть консоль восстановления. На сервере не должно быть рабочих данных и чужих приложений. Не используй эту инструкцию для машины работодателя.

Подготовь поддерживаемую Ubuntu, обычного пользователя с необходимыми административными правами, проверенный SSH-вход и Docker по официальной документации. Не отключай парольный вход, не меняй порт SSH и политику firewall одновременно с первым размещением: потерять управление проще, чем кажется. Разбор SSH-ключей есть в станции 7; первый fingerprint сверяется через доверенную консоль провайдера. Никому не передавай приватный ключ и пароль панели.

Повтори перенос из предыдущего шага, создав отдельную SSH-запись, например course-vps, с пользователем, публичным адресом и портом своего VPS. В командах переноса и туннеля задай VM_HOST=course-vps: не оставляй целью старую локальную VM. Сначала запусти только базовый compose.yaml и проверь его через SSH-туннель. Порты приложения 8080 и базы 5432 не открываем. Для первого удалённого опыта на этом можно остановиться: сервер уже удалённый, хотя API ещё не публичный.

2. Что добавляет HTTPS

Домен — понятное имя, DNS связывает его с адресом. Сам DNS не запускает приложение и не открывает firewall. TLS защищает канал и позволяет клиенту проверить имя сервера; он не решает, имеет ли конкретный пользователь право менять задачу. Поэтому проверка токена остаётся в API.

Для простого маршрута нужен принадлежащий тебе домен или поддомен. Создай A-запись на публичный IPv4 VPS. Если есть AAAA, IPv6 тоже должен вести на этот сервер и работать; неверный AAAA может ломать часть подключений и проверку сертификата. В первом опыте не добавляй CDN-прокси поверх DNS: иначе появится ещё один участник, который нужно отдельно настраивать и понимать.

  • Домен принадлежит тебе, A/AAAA проверены и указывают на нужный сервер.
  • По SSH есть рабочий вход и доступ к консоли восстановления.
  • Базовый API проверен на loopback через туннель.
  • На сервере свободны TCP 80 и 443. Входящие соединения разрешены в нужном облачном и хостовом фильтре.
  • У Caddy есть исходящий доступ к DNS и ACME — протоколу выдачи сертификатов.

Не полагайся только на UFW для опубликованных Docker-портов. Docker добавляет свои правила перенаправления; трафик может обходить ожидаемые UFW-правила. В этом примере внешние 80/443 открываются намеренно, а app остаётся на loopback. Не отключай Docker firewall и не сбрасывай таблицы фильтрации ради «починки». Конкретные правила провайдера проверяй по его документации, сохраняя SSH и консоль.

3. Включаем отдельный HTTPS-слой

Ниже tasks.example.org и email — заполнители. Они не дадут работающий сертификат; замени их своими значениями. Вводи эти команды только на подготовленном VPS, из каталога проекта. Имена не являются секретами, но не добавляй их в строгий файл .env: помощник разрешает в нём только три секретных переменных.

VPS · каталог service-workshop · после проверки всех условий
export COURSE_DOMAIN=tasks.example.org
export ACME_EMAIL=admin@example.org
unset APP_TOKEN POSTGRES_PASSWORD APP_DB_PASSWORD
docker compose -f compose.yaml -f compose.https.yaml config --quiet &&
docker compose -f compose.yaml -f compose.https.yaml up --build -d --wait --wait-timeout 240 &&
docker compose -f compose.yaml -f compose.https.yaml ps &&
docker compose -f compose.yaml -f compose.https.yaml logs --tail 50 caddy

Второй файл добавляет Caddy, публикации TCP 80/443 и отдельное хранилище его сертификатов. Он не заменяет loopback-привязку app и не публикует PostgreSQL. TCP 80 нужен для перенаправления HTTP и одного из способов ACME-проверки; 443 — для HTTPS и другого способа проверки. HTTP/3 по UDP 443 в этом примере не включён.

Успешный up --wait ещё не доказывает, что клиент из интернета принимает сертификат и достигает API. Caddy может работать как процесс, пока DNS или ACME-проверка ещё не исправлены. Проверка с внешней стороны обязательна. Не запускай бесконечные перевыпуски сертификата: у удостоверяющих центров есть ограничения частоты.

4. Проверяем с локального компьютера

Туннель для HTTPS-проверки не нужен. Сначала проверь только публичную общую health-точку без токена. Здесь снова укажи реальное доменное имя:

Локальный компьютер · реальный домен своего VPS
COURSE_DOMAIN=tasks.example.org
curl --connect-timeout 5 --max-time 15 -i "https://$COURSE_DOMAIN/health/ready"

Ожидается 200, без ошибки проверки сертификата и без перенаправления на чужой адрес. Если сертификат не подходит имени, просрочен или цепочка не доверена, остановись и исправь причину. Не добавляй -k: отключение проверки скрывает проблему, а не устраняет её.

Только после этого передай curl-конфиг данного VPS на локальную машину тем же способом, что для VM, но в новый приватный каталог .secrets-vps. Не используй конфиг локального проекта или другой VM. Для VPS с тем же каталогом загрузки пример выглядит так:

Локальный компьютер · запись course-vps настроена для своего VPS
VPS_HOST=course-vps
mkdir -m 700 .secrets-vps &&
scp "$VPS_HOST:course-workshop-upload/service-workshop/.secrets/client.curl" .secrets-vps/client.curl &&
chmod 600 .secrets-vps/client.curl &&
curl --config .secrets-vps/client.curl -i "https://$COURSE_DOMAIN/tasks"

Не отправляй Bearer-токен по публичному http://, даже «один раз для проверки». Не добавляй -L к авторизованному запросу без понимания цепочки перенаправлений. На управляемом корпоративном компьютере также учитывай доверенный HTTPS-прокси: для личных секретов используй разрешённое и понятное сетевое окружение.

Результат и границы

Ты увидел публичную цепочку DNS → TCP → TLS → reverse proxy → приложение → база. Это проверка учебного размещения, не аттестация безопасности и не доказательство высокой доступности. Для курса достаточно уметь объяснить каждый переход и показать обезличенные запросы; держать VPS включённым постоянно не требуется.

Проверяем и останавливаем

Работающий запрос — только начало. Проверим восстановление после остановки, сохранность данных и возможность завершить эксперимент без потери контроля.

1. Проверка «жив» не равна проверке «готов»

Выполняй этот эксперимент только на своём учебном Compose-проекте. Выбери одно окружение: локальный Docker или VM. Все команды ниже относятся к его каталогу и его loopback. Если работаешь на VM, выполняй их в SSH-сеансе. Не останавливай базу рабочего приложения.

Выбранный учебный Linux-хост · каталог service-workshop
docker compose stop db
curl --noproxy 127.0.0.1 --connect-timeout 2 --max-time 5 -i http://127.0.0.1:8080/health/live
curl --noproxy 127.0.0.1 --connect-timeout 2 --max-time 5 -i http://127.0.0.1:8080/health/ready
curl --config .secrets/client.curl -i http://127.0.0.1:8080/tasks

Ожидаем live → 200, ready → 503, tasks → 503. Процесс способен принять HTTP-запрос, но сейчас не может выполнить обещанную операцию с базой. Первая проверка нужна для обнаружения неработающего процесса; вторая — для решения, можно ли направлять ему рабочие запросы. Внешний мониторинг должен учитывать обе, а не объявлять сервис исправным по одному живому PID.

Тот же учебный Linux-хост · восстановление db
docker compose start db &&
docker compose up -d --wait --wait-timeout 90 &&
curl --config .secrets/client.curl -i http://127.0.0.1:8080/tasks &&
docker compose logs --tail 30 app

Список должен снова читаться, а прежние задачи сохраняться. Не меняй пароль и схему в середине этого опыта: тогда это уже другой отказ. Если db не становится healthy, начни с её логов. Время ожидания ограничено намеренно — бесконечное ожидание не является диагностикой.

Готовность базы и возможность быстро выполнить конкретное изменение — разные проверки. Например, блокировка нужной строки может задержать PUT при живой базе. В разборе полного бюджета запроса показано, как отделить ожидание исполнителя, ожидание соединения, SQL и отправку ответа. Там рассматривается следующий вариант архитектуры с пулом соединений; наш проект пока открывает соединение на операцию.

2. Резервная копия, которую действительно прочитали

Volume — не резервная копия. Он защищает от обычной замены контейнера, но не от ошибочного DELETE, потери диска или удаления volume. Сделаем логическую копию (описание схемы и данных в переносимом формате PostgreSQL) и восстановим её в другую, новую пустую базу. Нужны только собственные учебные данные и доверенный источник копии.

Сначала создай две задачи и измени одну, чтобы в таблице были разные ID и версии. Не меняй данные между сверками. Создай новый приватный каталог; если он уже существует, выбери новое имя и скорректируй пути:

Выбранный учебный Linux-хост · каталог service-workshop
mkdir -m 700 backups &&
(
  umask 077
  set -C
  docker compose exec -T db pg_dump -U postgres -d course_tasks \
    -Fc --no-owner --no-acl > backups/tasks-before-test.dump
)

-Fc выбирает архивный формат PostgreSQL, -T убирает псевдотерминал, чтобы бинарный вывод не был испорчен. Перенаправление > выполняет shell хоста, значит файл лежит не в контейнере. umask 077 ограничивает права нового файла; set -C запрещает перезапись существующего. Скобки ограничивают эти shell-настройки данным блоком. Если pg_dump завершился ошибкой, файл может существовать, но быть неполным: не считай наличие файла успехом.

Тот же учебный Linux-хост · проверить архив и создать НОВУЮ базу
docker compose exec -T db pg_restore --list < backups/tasks-before-test.dump
docker compose exec -T db createdb -U postgres --template=template0 course_tasks_restore_check

Продолжай только если createdb завершился успешно. Если база уже существует, не добавляй DROP, --clean и команды удаления: выбери новое имя и используй его последовательно. Следующий шаг никогда не должен указывать на исходную course_tasks.

Тот же учебный Linux-хост · восстановление только в новую restore_check
docker compose exec -T db pg_restore -U postgres \
  -d course_tasks_restore_check --exit-on-error --single-transaction \
  --no-owner --no-acl < backups/tasks-before-test.dump
docker compose exec -T db psql -U postgres -d course_tasks_restore_check \
  -v ON_ERROR_STOP=1 -c 'SELECT id, title, done, version FROM public.tasks ORDER BY id;'
docker compose exec -T db psql -U postgres -d course_tasks \
  -v ON_ERROR_STOP=1 -c 'SELECT id, title, done, version FROM public.tasks ORDER BY id;'

Сверь все значения, а не только число строк. Успешный pg_restore и совпадение данных показывают, что эту копию можно прочитать. --single-transaction делает данный restore одной транзакцией, --exit-on-error не позволяет молча продолжать после ошибки.

При восстановлении --no-owner запрещает применять исходное владение, а --no-acl — исходные разрешения. Архивный формат может сохранять сведения о владельце; нужное поведение здесь задаёт именно pg_restore. Восстановленная таблица принадлежит восстанавливающему администратору; course_app не получает автоматически рабочие разрешения в новой базе. Это проверка логической схемы и данных, не полное аварийное восстановление приложения. Для реального восстановления дополнительно проверяют роли, GRANT, настройки, миграции, секреты, подключение API и время возврата в работу. Копия на том же диске также не защищает от потери этого диска; переносить её нужно отдельно и безопасно, учитывая наличие данных внутри.

3. Обновление кода — отдельная операция

Правка исходника не меняет уже работающий процесс. В Compose нужно собрать новый образ и заменить контейнер app. Перед опытом сохрани рабочую редакцию исходников, результаты тестов и текущий образ. Потренируйся на нейтральном изменении, например дополнительном безопасном сообщении о старте, а не на несовместимой схеме данных.

Учебный Linux-хост · перед заменой app · имя образа запиши
docker compose images app
docker compose build app
docker compose up -d --wait --wait-timeout 90 app
curl --config .secrets/client.curl -i http://127.0.0.1:8080/tasks

Для осмысленного rollback (возврата на предыдущую версию) старый образ нужно заранее сохранить под отдельным тегом или digest и уметь выбрать его конфигурацией релиза. Сборка прежних исходников — другой, менее надёжный путь, потому что внешние базовые образы могли обновиться. Здесь мы не выдаём restart за доставку новой версии и не обещаем автоматический откат.

Отдельно подумай: если новая версия успела несовместимо изменить таблицу, поможет ли возврат одного бинарника? Нет — совместимость данных и приложения нужно планировать вместе. В этом практикуме init-скрипт не заменяет инструмент миграций. Более полный безопасный цикл релиза разобран в станции 10.

Под капотом выпуска: старое соединение и старая работа — не одно и то же

Наше пересоздание одного app не обещает выпуск без обрыва запросов. Чтобы понять дальнейшее развитие, сначала разбери что распределяет балансировщик: соединения или запросы, затем судьбу двух запросов при остановке экземпляра за прокси. Удаление из списка, локальный запрет новой работы и завершение уже принятой — разные действия. Эти разделы описывают нужный договор и его ограничения; одна команда Compose автоматически его не реализует.

4. Нагрузка — только на своём ограниченном стенде

Не запускай нагрузку на чужие адреса и публичную версию учебника. Для первого опыта достаточно последовательных запросов и пары одновременных клиентов; затем используй ограниченную локальную нагрузочную лабораторную станции 10. Учебный API требует токен для /tasks, поэтому готовый скрипт той лабораторной нужно согласовать с авторизацией: общий health-запрос не измеряет SQL-путь, а ответы 401 не означают пропускную способность CRUD.

Фиксируй число запросов в секунду, долю ошибок и задержки, а не «количество пользователей вообще». Один пользователь может отправлять запрос раз в минуту или сотни раз в секунду. При росте параллелизма следи за лимитом задач и соединениями базы. Останови опыт при ошибках или явной нехватке ресурсов; цель — понять предел и причину, а не любой ценой добиться красивой цифры.

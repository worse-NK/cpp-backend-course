1. Создание — это запрос и наблюдаемый результат

Сервер из предыдущего шага должен работать. Команды выполняй во втором терминале, из каталога проекта. Сначала убедимся, что защита действительно включена:

Локальный компьютер · терминал B · намеренно без токена
curl --noproxy 127.0.0.1 --connect-timeout 2 --max-time 5 -i http://127.0.0.1:8080/tasks

Ожидается 401. Это не «сервис сломан»: клиент не предъявил право доступа. Дальше конфиг клиента будет добавлять токен. Не вводим токен вручную в команду, чтобы не сохранять его в истории shell.

Локальный компьютер · терминал B · создать задачу
curl --config .secrets/client.curl -i \
  -H 'Content-Type: application/json' \
  --data '{"title":"Understand one HTTP request","done":false}' \
  http://127.0.0.1:8080/tasks

Обратная косая черта в конце строки продолжает одну shell-команду. После неё не должно быть пробелов. --data без явного метода выбирает POST. Заголовок Content-Type говорит серверу, что тело содержит JSON, а не форму.

Существенная часть ответа на первое создание в пустом хранилище

HTTP/1.1 201 Created
Location: /tasks/1
ETag: "v1"

{"done":false,"id":1,"title":"Understand one HTTP request","version":1}

Порядок заголовков и JSON-полей не важен. 201 сообщает о создании; Location указывает ресурс; ETag — метку этой версии представления. Идентификатор назначает сервер. Если ты уже создавал задачи, ID не обязан быть 1. Далее подставь фактический ID из своего ответа:

Локальный компьютер · терминал B · заменить 1 при необходимости
TASK_ID=1
curl --config .secrets/client.curl -i "http://127.0.0.1:8080/tasks/$TASK_ID"
curl --config .secrets/client.curl -i http://127.0.0.1:8080/tasks

TASK_ID — переменная текущего shell, а не настройка сервера. Двойные кавычки позволяют подставить её в URL. GET одной задачи возвращает объект и его ETag; GET списка — массив по возрастанию ID. В учебной реализации не более 1000 задач: это явная граница, а не обещание бесконечной выдачи.

2. Обновление: почему нужен If-Match

Представь двух клиентов, прочитавших версию 1. Первый отметил задачу выполненной. Второй всё ещё видит старую копию и меняет заголовок. Без проверки версии второй может незаметно вернуть done:false. Условное изменение означает: «запиши это только если текущая метка всё ещё та, которую я прочитал».

Локальный компьютер · терминал B · обновление прочитанной v1
curl --config .secrets/client.curl -i -X PUT \
  -H 'Content-Type: application/json' \
  -H 'If-Match: "v1"' \
  --data '{"title":"Understand one HTTP request","done":true}' \
  "http://127.0.0.1:8080/tasks/$TASK_ID"

Если задача всё ещё имеет версию 1, получишь 200, done:true и version:2. В этом PUT-ответе нет ETag: сервер преобразует переданное представление, добавляя управляемые им поля. По правилу HTTP нельзя выдавать validator (метку для последующей проверки версии) как будто принятые данные сохранены без преобразования. Чтобы получить актуальное представление и его ETag: "v2", выполни отдельный GET:

Локальный компьютер · терминал B · прочитать состояние после PUT
curl --config .secrets/client.curl -i "http://127.0.0.1:8080/tasks/$TASK_ID"

Теперь повтори ровно прежнюю PUT-команду с If-Match: "v1". Ожидается 412 Precondition Failed: условие уже ложно. Повтор не должен незаметно перезаписать новую версию. Предварительное условие защищает момент изменения, а не резервирует ресурс навсегда: после GET другой клиент снова может изменить задачу, и следующий PUT тогда тоже получит 412.

Наш API намеренно принимает только одну сильную метку вида "vN", где N — положительное десятичное число без ведущих нулей в диапазоне signed 64-bit. Списки меток, * и слабые метки W/… здесь не реализованы. Это учебное подмножество, не полный синтаксис HTTP If-Match. Сервер возвращает 428, когда условие отсутствует, 400 — когда этот поддерживаемый формат нарушен, 412 — когда подходящей текущей версии нет.

Граница простой метки vN. Она подходит только для неизменной схемы представления и непрерывной истории идентификатора/версии. Нативный memory-режим при перезапуске теряет всю историю, поэтому старые ID и метки надо отбросить: он не обещает защиту старого клиента после повторного создания хранилища. Для многопроцессного и долговечного API нужна согласованная политика идентификаторов и валидаторов, учитывающая восстановление данных и изменение представления. Одна локальная переменная version этого не обеспечивает.

Что делать клиенту после 412?

Сначала заново прочитать задачу. Потом решить, как совместить своё намерение с новым состоянием, и только после этого отправить изменение с актуальным ETag. Слепое повторение со «свежей меткой любой ценой» убирает смысл защиты. После сетевого таймаута тоже нельзя автоматически считать, что запись не произошла: проверь наблюдаемое состояние.

3. Различаем ошибки входа

Для POST и PUT разрешены ровно два поля: непустой UTF-8 заголовок title длиной до 200 байт без нулевого символа и булево done. Кириллическая буква обычно занимает больше байта; лимит в байтах — не обещание 200 любых символов. ID и версию нельзя назначить из тела.

Локальный компьютер · терминал B · намеренно неправильный тип
curl --config .secrets/client.curl -i \
  -H 'Content-Type: application/json' \
  --data '{"title":"Wrong type","done":"false"}' \
  http://127.0.0.1:8080/tasks

Ожидается 422: JSON корректен синтаксически, но строка "false" — не булево значение false. Из-за fail-with-body в конфиге curl завершится с ненулевым кодом и всё равно покажет ответ. Для намеренных ошибок это ожидаемо.

Измени запросОжидаемый статусЧто именно проверили
Оборви JSON после { или повтори ключ title400Синтаксис и однозначность JSON.
Добавь поле id, убери done, передай пустой title422Допустимая схема данных.
Убери заголовок Content-Type из POST415Поддерживаемый формат тела.
Отправь тело больше 4096 байт413Ограничение объёма входа, не замена проверке схемы.
GET допустимого ID, которого нет404Такого ресурса нет. ID записывается без ведущих нулей: от 1 до 9223372036854775807.
GET с ID 01, 0 или числом вне диапазона400Идентификатор не соответствует контракту, а не просто отсутствует в хранилище.
PUT без If-Match428Клиент не дал обязательное предусловие.

Выбери два неправильных запроса и исправь их сам. Цель — уметь по статусу отделить отсутствие соединения, отсутствие доступа, неверный формат и конфликт состояния. Не учи номера в отрыве от запроса.

4. Удаление и потеря памяти процесса

Локальный компьютер · терминал B · после успешного PUT до v2
curl --config .secrets/client.curl -i -X DELETE \
  -H 'If-Match: "v2"' "http://127.0.0.1:8080/tasks/$TASK_ID"
curl --config .secrets/client.curl -i "http://127.0.0.1:8080/tasks/$TASK_ID"

DELETE с текущей меткой возвращает 204 без тела; последующий GET — 404. Если ты делал дополнительные изменения, сначала прочитай настоящий ETag. Повтор DELETE с прежней меткой вернёт 412, потому что текущего представления уже нет. Идемпотентность метода не требует одинакового статуса каждого повтора.

Снова создай одну задачу. В терминале A нажми Ctrl-C, дождись завершения и запусти python3 lab.py run. GET списка покажет []. Это не ошибка базы: её ещё нет. Все данные принадлежали памяти завершившегося процесса. Перед следующим этапом останови нативный процесс, чтобы освободить порт 8080.

Проверь себя без подсказки

  1. Почему 401 доказывает больше о доступности сервера, чем Connection refused?
  2. Почему повтор старого PUT даёт 412, а не ещё одно успешное изменение?
  3. Где были задачи и почему перезапуск их потерял?

Сохрани свои команды и обезличенные статусы в заметку. Токен и заголовок Authorization в неё не входят.

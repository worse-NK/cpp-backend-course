Ограниченная нагрузка: измеряем настоящий путь к задачам

Сначала выполни обычный авторизованный GET и создай одну–три учебные задачи. Выбери одно уже работающее окружение: нативный процесс или свой Compose-проект. Не запускай опыт на чужом сервисе, рабочем приложении или публичном сайте курса. Для PostgreSQL-варианта запрос /tasks проходит через хранилище и SQL; ответ health-точки или быстрый 401 этот путь не проверяет.

В исходниках есть готовый load.py, которому достаточно Python 3.10+ без дополнительных пакетов. Он выполняет только GET /tasks: не создаёт записи, не выключает базу и не перезапускает приложение. Токен читает из созданного ранее приватного .secrets/client.curl, не выводит его и не принимает секрет через аргумент командной строки. Нельзя подставить произвольный интернет-адрес: допустим только числовой loopback с явно указанным непривилегированным портом. Перенаправления не выполняются, настройки HTTP-прокси из окружения не используются.

recovery — после нагрузки10 запросов, один исполнительПроверка возвращения к малому параллелизму; это не автоматическое восстановление выключенной базы.

Между фазами небольшая пауза. Всего отправляется не более 64 запросов, каждому отводится до двух секунд сетевого ожидания, всему сценарию — 30 секунд. При истечении общего бюджета новые запросы не начинаются, а незапущенные явно учитываются. Паузы также входят в бюджет. Системное планирование может немного задержать завершение процесса: это ограниченный эксперимент, не таймер реального времени.

Модель называется закрытой конкурентностью: число одновременно работающих исполнителей задано, но частота запросов не зафиксирована. Замедлился сервер — каждый исполнитель реже начинает следующий запрос. Поэтому четыре исполнителя — не «четыре пользователя вообще» и не заданные 100 запросов в секунду. Здесь каждый запрос открывает новое TCP-соединение, не использует HTTP keep-alive и не повторяется автоматически. Измерение включает этот выбор; его нельзя без оговорок сравнивать с тестом постоянных соединений или выдавать за предел сервера.

Как прочитать результат

Например, строка ниже означает, что вся исходная фаза завершилась по ожидаемому контракту; числа задержек у тебя будут свои:

baseline: workers=1 completed=10/10 valid=10 not_started=0
  outcomes={"valid": 10}
  HTTP statuses={"200": 10}

valid — не просто статус 200. Клиент получил тело целиком, разобрал строгий JSON и проверил массив задач: точные поля, типы, пределы значений и возрастающий порядок ID. Страница HTML со статусом 200, JSON health-точки, дублирующиеся поля или слишком большое тело успешной операцией не считаются. Пустой корректный список допустим, но в этом опыте заранее созданная задача помогает убедиться, что проверяется нужное хранилище. Изменения данных другими клиентами во время измерения лучше исключить.

Отдельно показаны auth_401 (не подошёл токен), unavailable_503 (API сообщил недоступность), прочие HTTP-статусы, ошибки соединения и тайм-ауты. При 401, перенаправлении или неправильном успешном ответе клиент прекращает новые отправки: нагружать не тот сервис бессмысленно. Уже начатые запросы завершаются в своих пределах. Ошибки и пропущенные запросы дают ненулевой код завершения, не «успешную производительность».

valid responses/s — число проверенных успешных ответов, делённое на время фазы. Два набора задержек сохраняют разные выборки: all latency включает все завершённые попытки, valid latency — только успешные. Возле каждого указан размер выборки n. Клиент измеряет время от начала подключения до полного чтения и проверки ответа по монотонным часам (их ход не меняется при коррекции календарного времени).

p50, p95, p99 — значения на соответствующих местах отсортированной выборки, с округлением номера места вверх. У десяти ответов p99 окажется максимальным; это ещё не надёжная оценка редкого хвоста задержек. Малый опыт нужен для понимания и сравнения фаз, не для заявления о промышленной ёмкости. Для большего, всё ещё ограниченного опыта можно выполнить python3 load.py --workers 4 --requests 100. Жёсткие верхние пределы клиента: восемь исполнителей, 400 запросов нагрузочной фазы, 500 суммарно, пять секунд на запрос и 60 секунд на сценарий; тело ответа — не более 2 МиБ при явной настройке, заголовки — не более 16 КиБ. Не повышай все параметры одновременно.

Клиентское время и серверный журнал — разные границы

В другом терминале своего Compose-проекта посмотри docker compose logs --tail 80 app; у нативного процесса журнал виден в его терминале. Сообщение содержит шаблон маршрута, статус и интервалы handler_us и storage_us в микросекундах. handler_us охватывает работу внутри обработчика, включая его проверки и формирование JSON. storage_us — длительность вызова хранилища: в памяти это может включать ожидание мьютекса, в PostgreSQL — открытие соединения, ожидание и выполнение SQL. Это не отдельное «чистое время SQL».

В эти интервалы не входят ожидание исполнителя в очереди библиотеки, предшествующие разбор HTTP и проверка авторизации, а также отправка ответа в сокет. Для ранних отказов вместо заимствованных у другого запроса чисел пишется not_measured. Сервер использует std::chrono::steady_clock. Его длительности можно сравнивать по смыслу с клиентскими длительностями, но отметки разных часов не надо вычитать друг из друга.

Если клиентская задержка выросла, а время обработчика осталось небольшим, сначала проверь очереди, создание соединений, ресурс клиента и передачу ответа, а не объявляй SQL медленным. Разность p99 клиента и p99 обработчика не даёт p99 ожидания очереди: это могут быть разные запросы и разные выборки. В закреплённой версии cpp-httplib журнал вызывается до окончательной отправки ответа, поэтому серверная запись status=200 сама по себе не доказывает, что клиент получил тело. Сопоставляй журналы с результатами клиента, а не заменяй ими проверку доставки.

Повторяем после отказа или через SSH-туннель

Это дополнительный опыт только для Compose-варианта, не обязательный шаг первого измерения. Сначала запиши baseline исправного стенда. Затем перейди к инструкции контролируемой остановки своей db: там подписаны окружение, команда остановки, проверки live/ready и команды возврата. Если ещё не готов управлять этим отказом, пропусти опыт. Вернувшись сюда с остановленной учебной базой, выполни короткую фазу без успешного прогрева:

Тот же собственный учебный хост · база остановлена предыдущим контролируемым опытом
python3 load.py --phase load --warmup 0 --workers 2 --requests 8 --max-runtime 15

Ожидаемый смысл — ноль корректных ответов со списком задач и отдельно посчитанные 503; результат не должен быть PASS. Если вместо них есть тайм-ауты или ошибки соединения, не подменяй наблюдение ожиданием: проверь процесс, логи и заданные сроки. Сам скрипт не включает базу обратно. Восстанови её указанными там командами start/up, дождись готовности и выполни:

Тот же собственный учебный хост · после восстановления готовности базы
python3 load.py --phase recovery --warmup 1

Должны снова проходить проверку реальные задачи. Нативный режим не использует PostgreSQL: остановка контейнера базы не является отказом его хранилища. Для проверки через уже открытый локальный SSH-туннель укажи его порт и полученный ранее конфиг именно удалённого проекта:

Локальный компьютер · каталог service-workshop · туннель на VM уже работает
python3 load.py --base-url http://127.0.0.1:18080 --client-config .secrets-vm/client.curl

Этот вариант дополнительно измеряет путь через SSH и другую машину. Клиент всё равно соединяется только с локальным слушателем туннеля. Не подставляй публичный URL и не публикуй 8080 ради нагрузки. В отчёте укажи окружение, число задач, параметры, успешные ответы, ошибки, задержки и различие фаз; не прикладывай токены и содержимое приватных конфигов.

Границы измерения и первоисточники

  • Python: HTTPConnection и HTTPResponse, тайм-аут сокета и монотонные часы. Тайм-аут одной блокирующей операции сам по себе не является общим сроком запроса, поэтому клиент дополнительно прерывает свой сокет по дедлайну.
  • Открытый проект C++20 N4861: steady_clock.
  • Закреплённый исходник cpp-httplib 0.59.0 и границы измерений нашего приложения.

У Анны и Бориса есть приложение со списками дел. Каждый видит и переименовывает только свои записи. Когда появляется новое дело, отдельный обработчик увеличивает счётчик созданных дел. Представим, что приложение закрылось сразу после сохранения записи: дело уже есть, но пользователь не получил ответа. Или событие дошло до обработчика дважды. Здесь проверим, как продолжить работу и не потерять событие, не создать лишнюю задачу и не прибавить счётчик повторно.

Это следующий самостоятельный локальный опыт, а не новая настройка прежнего Task API. Используем настоящие C++-программы, PostgreSQL и RabbitMQ; затем отдельно — две PostgreSQL-базы, чтобы увидеть отставание и восстановление копии. Запускай из полной локальной копии репозитория на своём Linux/WSL-компьютере. Старый архив основного сервиса, созданный lab.py pack, эти вложенные лаборатории не включает.

1. Что именно свяжем

Счётчик отражает число фактов создания, а не HTTP-запросов, публикаций или переименований. Это намеренно небольшой эффект: по нему легко проверить повтор. Подобная защита SQL-счётчика не распространяется автоматически на внешний платёж или отправленное письмо.

Граница опыта: локальный HTTP и AMQP без TLS, без защиты входа от перебора, без браузерных cookies, одного брокера и одной основной БД достаточно только для учебного запуска. Не подставляй рабочие пароли и не открывай этот стенд в интернет. У БД и брокера нет опубликованных портов. API дополнительно подключён к bridge-сети, но его единственный host-порт привязан к 127.0.0.1; это не запрет всех исходящих соединений API.

2. Подготовим отдельную программу и войдём двумя пользователями

Понадобятся Python 3 и локальный Docker с Compose v2. Сборка загружает закреплённые исходные архивы библиотек и устанавливает зависимости только в образ, не на хост. Два задания сборки выполняются параллельно; первый запуск может занять несколько минут. Из корня репозитория:

Локальный компьютер · полная копия репозитория
cd roadmap/examples/service-workshop/production-path-lab &&
python3 lab.py init --port 8089 &&
python3 lab.py check &&
python3 lab.py build &&
python3 lab.py up &&
python3 lab.py login --user alice &&
python3 lab.py login --user bo

init создаёт новый случайный проект и приватные секреты. Если порт занят, выбери другой до инициализации. Существующий .state не перезаписывается. Helper проверяет локальный Docker endpoint и метки своих ресурсов; ему нельзя передать чужое имя проекта. При ошибке выполняй диагностику, не добавляй удаление volume «на всякий случай».

У аккаунтов Alice и Bo сгенерированы разные случайные пароли. Они не показываются в терминале. При входе libsodium проверяет пароль по сохранённому проверочному значению Argon2id; API выдаёт новый случайный bearer token (секрет для следующих обращений). Helper сохраняет токен в файле 0600 и передаёт только в Authorization. В таблице сессий остаётся BLAKE2b-хеш токена, не его исходное значение. Быстрый хеш допустим здесь для случайного 256-битного секрета; им нельзя заменять замедленную проверку человеческого пароля.

Каталог .state имеет права 0700. Файлы для контейнеров читаемы как 0444 внутри этого закрытого каталога: обычные Compose file secrets не переназначают UID файлов. Каждый сервис получает только нужные ему mounts. Не делай каталог общедоступным и не отправляй его содержимое, полную конфигурацию или environment. Администратор Docker и root хоста всё равно могут прочитать секреты; это не хранилище секретов промышленной системы.

3. Задача уже появилась — счётчик ещё нет

Тот же каталог · новый стенд
python3 lab.py create --user alice --key create-a --title 'Prepare report' &&
python3 lab.py tasks --user alice &&
python3 lab.py tasks --user bo &&
python3 lab.py total --user alice &&
python3 lab.py inspect

У Alice появится одна задача с версией 1; у Bo список пуст. Счётчик Alice пока 0. inspect покажет одну задачу, одну pending-запись outbox и ноль receipts. Pending означает «обязанность ещё не отмечена отправленной», receipt — «этот обработчик уже применил событие». SQL-транзакция API фиксирует задачу, результат команды и outbox вместе; отдельно работающий брокер этой транзакцией не управляется.

Повтори точный POST с ключом create-a: ID и исходный результат сохранятся, второй задачи не будет. Тот же ключ с другим title даст 409. Bo может использовать строку create-a для своей другой команды: область ключа включает установленного пользователя. owner_id из тела не принимается; владельца API берёт только из действующей сессии.

Отправим и применим одно событие
python3 lab.py relay &&
python3 lab.py consume &&
python3 lab.py total --user alice &&
python3 lab.py inspect

Теперь счётчик 1. Relay публикует persistent-сообщение с постоянным event_id, ждёт publisher confirm и лишь затем пишет sent_at. Consumer одной транзакцией вставляет уникальный (consumer,event_id) и увеличивает счётчик только для новой вставки. После COMMIT он отправляет manual ack. Публикация может повториться, доставка может повториться, но выбранный SQL-эффект повторяться не должен.

Каждая команда relay/consume выполняет не более одной работы. Это управляемое наблюдение, не демон непрерывной обработки. FOR UPDATE SKIP LOCKED позволяет отправителям не ждать занятую строку, но не гарантирует общий порядок. Здесь сложение счётчика от порядка не зависит. Очередь одного узла quorum не превращает стенд в отказоустойчивый кластер; предел очереди с reject-publish не является точной границей памяти или числа сообщений в полёте.

4. Три границы, на которых действительно завершим процесс

Перед каждым опытом выясни, что уже стало устойчивым, а что ещё не подтверждено

Полные команды и ожидаемые состояния: README, раздел «Три настоящих падения процессов». Режимы задаются только локальными командами запуска; HTTP-клиент не может включить их заголовком. Для API используй api-crash, для отправителя — relay --fault, для получателя — consume --fault. Соответствующие коды 86/87/88 — намеренное завершение, не повод сбрасывать данные.

Команды с ожидаемым падением выполняются отдельно, без && перед восстановлением. После API-падения верни api-normal и повтори исходный запрос. После relay-падения ожидай одну новую обработку и duplicate при двух последовательных consume. После consumer-падения повторная выдача будет распознана по прежнему receipt. Не путай публикационный дубликат с redelivered: флаг описывает повторную выдачу конкретной доставки, а не одинаковый бизнес-ID в разных публикациях.

Здесь память действительно исчезает вместе с процессом. Защита не хранится в std::set работающего API. При этом перезапуск контейнера не равен потере диска, а успешная проверка счётчика не доказывает все возможные конкурентные расписания или ровно одну сетевую доставку.

5. Проверим прекращение доступа, а не только кнопку выхода

Переименование выполняет условный SQL: ID задачи, установленный пользователь и ожидаемая версия входят в WHERE. Чужая или отсутствующая задача даёт 404, устаревшая версия собственной — 409. При отказе проверь и исходную строку: один HTTP-статус не доказывает отсутствие изменения. Копируемый пример с ID/version и автоматическая проверка чужих запросов находятся в README.

Выход · вторую строку запускай как ожидаемый отказ
python3 lab.py logout --user alice
python3 lab.py tasks --user alice

Вторая команда всё ещё отправляет сохранённый токен, но должна получить 401: отзыв записан на сервере. Новый login выдаёт новый токен и заменяет прежнюю сессию этого пользователя. Политика здесь — одна сессия на пользователя, 20 минут от входа и 5 минут с проверки сессии последней успешно зафиксированной защищённой операции. Отметка ставится при проверке, а не отправке HTTP-ответа; отказ её откатывает. Это условия опыта, не обязательные сроки для любого продукта.

Для проверки без ожидания выполни login, затем expire-idle --user alice и отдельно tasks. Повтори с expire-absolute. Эти команды администратора меняют временные поля только учебной сессии; системные часы не трогаются. API проверяет сессию при каждом защищённом действии. Её строка блокируется до завершения операции; logout использует ту же строку. Уже начавшийся запрос автоматически не отменяется: правило определяет границу следующих разрешений.

6. Автоматический повтор на чистом стенде

Тот же каталог · создаётся другой случайный проект
python3 test_lab.py &&
python3 acceptance.py --run-local-docker --report /tmp/course-path-my-acceptance.json

Приёмка не трогает текущие задачи: копирует публичные исходники во временную папку, выбирает другое случайное имя и свободный loopback-порт, собирает приложение. Она проверяет оба вида повторов, три падения, права Alice/Bo, истечение и отзыв сессий, перезапуски БД/брокера, отказ отправки при остановленном брокере и возврат доставки после недоступной БД получателя. После проверки меток удаляются только собственные временные контейнеры, сети и два volume; это необратимый сброс их учебных данных. Приватный JSON-отчёт сохраняется, секреты в него не записываются. Существующий отчёт не перезаписывается.

Свой ручной стенд останавливай командой python3 lab.py down: volume сохранятся. Только если сознательно нужен пустой повтор, используй down --delete-data. Удалятся исключительно два проверенных volume этого проекта; вернуть их содержимое без резервной копии нельзя. Настройки останутся, старые токены после нового создания базы уже не действуют.

7. Отдельный опыт: получено репликой — ещё не видно в SELECT

У списка дел появляется копия БД для чтения. В основной базе записана новая задача, но на копии её пока нет. Проверим это на настоящей потоковой репликации PostgreSQL 18, затем остановим старую основную базу, вручную назначим новую и заново создадим её копию из физической резервной копии. Этот опыт не использует API, брокер или их volume.

Тот же каталог · только свежие PostgreSQL-контейнеры, без host-портов
python3 replication_lab.py --run-local-docker --interactive \
  --report /tmp/course-pg-recovery-my-run.json

Нужен локальный образ postgres:18-bookworm, уже используемый предыдущим стендом. Флаг --interactive останавливает последовательность перед каждым этапом: сначала прочитай следующий пункт, затем нажми Enter. Без него выполняются те же проверки подряд. Ctrl-C приводит к очистке только ресурсов этого опыта. Отчёт должен быть новым файлом.

  1. Исходная копия. В primary одна задача. pg_basebackup -R -X stream копирует весь небольшой кластер и создаёт standby — сервер, продолжающий применять журнал primary. На standby видна задача, но запись отвергается: он в recovery (восстановлении по журналу).
  2. Приём отдельно от применения. Запросим паузу pg_wal_replay_pause() и дождёмся именно состояния paused. После этого primary фиксирует вторую задачу. Копия продолжает получать и сохранять WAL, но не применяет его: primary показывает 2 строки, standby — 1. Отчёт содержит фактические receive/replay LSN (позиции в журнале), не вымышленные миллисекунды задержки.
  3. Продолжение. После resume дождёмся второй строки и нужной replay-позиции. В этом опыте выбрана асинхронная репликация: обычный primary COMMIT сам по себе не ждал видимости строки на standby.
  4. Безопасная учебная смена роли. Прежде чем вызвать pg_promote, helper останавливает старую primary, проверяет завершение процесса и отключает контейнер от единственной сети опыта. Только после этого standby становится writable и принимает третью задачу. Это ручное fencing (лишение старого узла возможности обслуживать клиентов) в рамках одного контролируемого хоста; не распределённая система автоматического выбора лидера.
  5. Вернулся старый узел. Запустим прежнюю БД только в подтверждённой сетевой изоляции, без портов. Она всё ещё считает себя primary и содержит 2 строки, в отличие от 3 у нового сервера. Нельзя вернуть её клиентам только потому, что процесс снова жив. Helper не направляет к ней прикладные записи и снова останавливает.
  6. Новая копия. Старый volume не переписывается «поверх»: он остаётся отключённым до очистки. Из новой primary делается свежий физический base backup в другой пустой volume. Новая standby видит третью задачу, затем получает четвёртую уже потоковой репликацией. Это восстановление копии из актуального источника, не выполненный pg_rewind или PITR (восстановление на выбранный момент по архиву WAL).

Контрольная пауза доказывает различие получения и применения. Смена роли выполняется после проверенного догоняния и остановки старого узла, поэтому этот конкретный прогон сохраняет заданные строки. Он не доказывает отсутствие потерь при произвольной аварии: асинхронная репликация допускает окно потери данных. Нет автоматического failover, переключения HTTP-клиентов, независимых машин, потери диска или измерения RTO/RPO под нагрузкой. Репликационный slot удерживает нужный журнал, но тоже требует контроля места; здесь объём мал и время ожидания ограничено.

Что должно остаться после опыта

  • Таблица трёх границ: зафиксировано, подтверждено, можно повторить.
  • Два пользователя и наблюдаемый отказ чужого изменения без побочного эффекта.
  • Серверный отказ старой, истёкшей и отозванной сессии.
  • Receipt и счётчик пережили завершение процесса и перезапуск БД.
  • Реальные receive/replay-позиции и 2 строки против 1 при паузе.
  • Старая primary остановлена и изолирована до promotion; возвращённая копия не назначена лидером автоматически.
  • Новая standby развёрнута из base backup и принимает дальнейший WAL.
  • В отчёте сохранены границы проверенного, а не утверждение о готовой production-системе.

Исходники: инструкция, API, relay и consumer, схема и роли, опыт с репликацией. К теории: 11 · связка доставки, 15 · реальные сессии, 9B · восстановление копии.

Основания и границы

  • PostgreSQL 18: row locks и SKIP LOCKED; Read Committed и конкурирующее обновление.
  • RabbitMQ 4.4: publisher confirm и consumer ack; quorum queues, пределы и delivery count.
  • libsodium: парольная проверка; случайный токен; BLAKE2b для случайного секрета.
  • OWASP: жизненный цикл, сроки и серверный отзыв сеанса.
  • PostgreSQL 18: receive/replay, реальное состояние паузы и promotion; асинхронная потоковая репликация и slots; старый primary и fencing; физическая резервная копия и -R/-X.

Сроки сессии, размеры очереди и искусственная пауза заданы лабораторией. Фактические версии и LSN записывает запуск. Успешный прогон не является криптографическим аудитом, автоматической HA-системой или доказательством сохранности после потери диска.

Этот шаг необязателен. Основной практикум уже дал настоящий удалённый запуск в VM. VPS полезен, если хочешь увидеть публичный адрес, DNS, сертификат и ответственность за доступный из интернета сервис. Аренда и домен могут стоить денег; обещание бесплатного бессрочного сервера здесь не даётся.

1. VPS не меняет смысл команд

VPS (виртуальный выделенный сервер) — Linux-машина у провайдера. Ты получаешь доступ по SSH и управляешь процессами почти так же, как в своей VM, но машина обычно имеет публичный IP и постоянно встречает посторонние попытки подключения. Считай её отдельным окружением: новые секреты, свой volume и свой каталог проекта.

Выбирай небольшой Linux-сервер с ресурсами не меньше учебной VM и понятным способом удаления. До оплаты проверь стоимость диска, публичного IP, трафика и резервных копий: выключенная машина не обязательно перестаёт оплачиваться. Убедись, что есть консоль восстановления. На сервере не должно быть рабочих данных и чужих приложений. Не используй эту инструкцию для машины работодателя.

Подготовь поддерживаемую Ubuntu, обычного пользователя с необходимыми административными правами, проверенный SSH-вход и Docker по официальной документации. Не отключай парольный вход, не меняй порт SSH и политику firewall одновременно с первым размещением: потерять управление проще, чем кажется. Разбор SSH-ключей есть в станции 7; первый fingerprint сверяется через доверенную консоль провайдера. Никому не передавай приватный ключ и пароль панели.

Повтори перенос из предыдущего шага, создав отдельную SSH-запись, например course-vps, с пользователем, публичным адресом и портом своего VPS. В командах переноса и туннеля задай VM_HOST=course-vps: не оставляй целью старую локальную VM. Сначала запусти только базовый compose.yaml и проверь его через SSH-туннель. Порты приложения 8080 и базы 5432 не открываем. Для первого удалённого опыта на этом можно остановиться: сервер уже удалённый, хотя API ещё не публичный.

2. Что добавляет HTTPS

Домен — понятное имя, DNS связывает его с адресом. Сам DNS не запускает приложение и не открывает firewall. TLS защищает канал и позволяет клиенту проверить имя сервера; он не решает, имеет ли конкретный пользователь право менять задачу. Поэтому проверка токена остаётся в API.

Для простого маршрута нужен принадлежащий тебе домен или поддомен. Создай A-запись на публичный IPv4 VPS. Если есть AAAA, IPv6 тоже должен вести на этот сервер и работать; неверный AAAA может ломать часть подключений и проверку сертификата. В первом опыте не добавляй CDN-прокси поверх DNS: иначе появится ещё один участник, который нужно отдельно настраивать и понимать.

  • Домен принадлежит тебе, A/AAAA проверены и указывают на нужный сервер.
  • По SSH есть рабочий вход и доступ к консоли восстановления.
  • Базовый API проверен на loopback через туннель.
  • На сервере свободны TCP 80 и 443. Входящие соединения разрешены в нужном облачном и хостовом фильтре.
  • У Caddy есть исходящий доступ к DNS и ACME — протоколу выдачи сертификатов.

Не полагайся только на UFW для опубликованных Docker-портов. Docker добавляет свои правила перенаправления; трафик может обходить ожидаемые UFW-правила. В этом примере внешние 80/443 открываются намеренно, а app остаётся на loopback. Не отключай Docker firewall и не сбрасывай таблицы фильтрации ради «починки». Конкретные правила провайдера проверяй по его документации, сохраняя SSH и консоль.

3. Включаем отдельный HTTPS-слой

Ниже tasks.example.org и email — заполнители. Они не дадут работающий сертификат; замени их своими значениями. Вводи эти команды только на подготовленном VPS, из каталога проекта. Имена не являются секретами, но не добавляй их в строгий файл .env: помощник разрешает в нём только три секретных переменных.

VPS · каталог service-workshop · после проверки всех условий
export COURSE_DOMAIN=tasks.example.org
export ACME_EMAIL=admin@example.org
unset APP_TOKEN POSTGRES_PASSWORD APP_DB_PASSWORD
docker compose -f compose.yaml -f compose.https.yaml config --quiet &&
docker compose -f compose.yaml -f compose.https.yaml up --build -d --wait --wait-timeout 240 &&
docker compose -f compose.yaml -f compose.https.yaml ps &&
docker compose -f compose.yaml -f compose.https.yaml logs --tail 50 caddy

Второй файл добавляет Caddy, публикации TCP 80/443 и отдельное хранилище его сертификатов. Он не заменяет loopback-привязку app и не публикует PostgreSQL. TCP 80 нужен для перенаправления HTTP и одного из способов ACME-проверки; 443 — для HTTPS и другого способа проверки. HTTP/3 по UDP 443 в этом примере не включён.

Успешный up --wait ещё не доказывает, что клиент из интернета принимает сертификат и достигает API. Caddy может работать как процесс, пока DNS или ACME-проверка ещё не исправлены. Проверка с внешней стороны обязательна. Не запускай бесконечные перевыпуски сертификата: у удостоверяющих центров есть ограничения частоты.

4. Проверяем с локального компьютера

Туннель для HTTPS-проверки не нужен. Сначала проверь только публичную общую health-точку без токена. Здесь снова укажи реальное доменное имя:

Локальный компьютер · реальный домен своего VPS
COURSE_DOMAIN=tasks.example.org
curl --connect-timeout 5 --max-time 15 -i "https://$COURSE_DOMAIN/health/ready"

Ожидается 200, без ошибки проверки сертификата и без перенаправления на чужой адрес. Если сертификат не подходит имени, просрочен или цепочка не доверена, остановись и исправь причину. Не добавляй -k: отключение проверки скрывает проблему, а не устраняет её.

Только после этого передай curl-конфиг данного VPS на локальную машину тем же способом, что для VM, но в новый приватный каталог .secrets-vps. Не используй конфиг локального проекта или другой VM. Для VPS с тем же каталогом загрузки пример выглядит так:

Локальный компьютер · запись course-vps настроена для своего VPS
VPS_HOST=course-vps
mkdir -m 700 .secrets-vps &&
scp "$VPS_HOST:course-workshop-upload/service-workshop/.secrets/client.curl" .secrets-vps/client.curl &&
chmod 600 .secrets-vps/client.curl &&
curl --config .secrets-vps/client.curl -i "https://$COURSE_DOMAIN/tasks"

Не отправляй Bearer-токен по публичному http://, даже «один раз для проверки». Не добавляй -L к авторизованному запросу без понимания цепочки перенаправлений. На управляемом корпоративном компьютере также учитывай доверенный HTTPS-прокси: для личных секретов используй разрешённое и понятное сетевое окружение.

Результат и границы

Ты увидел публичную цепочку DNS → TCP → TLS → reverse proxy → приложение → база. Это проверка учебного размещения, не аттестация безопасности и не доказательство высокой доступности. Для курса достаточно уметь объяснить каждый переход и показать обезличенные запросы; держать VPS включённым постоянно не требуется.

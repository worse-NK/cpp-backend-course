Может ли поиск
показать лишнее?

На сайте есть опубликованные статьи и ещё не готовые черновики. Разберём, почему поиск должен показывать посетителю только открытые материалы — независимо от того, что он написал в строке поиска.

Сначала — сама задача

Представим сайт с учебными статьями. Авторы готовят новые тексты и пока держат их в черновиках, а посетители читают опубликованное. У посетителя есть строка поиска: он вводит название и получает подходящую открытую статью. В этом опыте проверим, может ли изменение текста поиска заставить сайт показать чужие черновики.

В нашем маленьком каталоге четыре опубликованных материала и два черновика. Ищем по точному названию, не по части слова. Для допустимого открытого названия должна найтись его статья; для отсутствующего названия — ничего. Черновики не должны появляться в ответе, даже если посетитель знает их названия.

Данные хранятся в таблице: одна строка — один материал, а столбцы — его свойства. title хранит название; is_public отмечает публикацию: 1 — опубликовано, 0 — черновик.

После нажатия «Найти» обработчик (код приложения, выполняющий поиск) готовит команду для базы данных. Такие команды записывают на SQL — языке для работы с базами данных. Наша команда должна означать: «Найти опубликованные материалы с указанным названием».

Данные этого примера

Все шесть записей вымышлены. Перед каждым запуском они восстанавливаются. Мы ничего не удаляем и не обращаемся к чужому серверу.

Что будем проверять

В начальной версии введённое название вставляется прямо в текст команды. Посмотрим, может ли это изменить само условие поиска. Затем сравним исправления. Писать код не нужно: вводим текст, запускаем поиск и разбираем результат.

SQLite — библиотека, которая здесь хранит таблицу и выполняет SQL-команды прямо в браузере. HTTP и C++ — дополнительные пояснения, а не работающий сервер.

Для первого знакомства переходи по этапам по порядку. Можно свободно открыть любой этап или вернуться к уже просмотренному.

Разобрать SQL и причину нарушения по шагам
SELECT перечисляет столбцы результата, FROM lessons выбирает таблицу. Часть после WHERE задаёт условие для каждой строки. Здесь нужны одновременно публикация и совпадение названия: is_public = 1 AND title = ….
Одинарные кавычки ограничивают строковое значение SQL. В уязвимом варианте введённая кавычка может закрыть это значение. Тогда OR 1=1 уже разбирается как часть условия, а не как часть названия.
В этом запросе AND связывает выражения сильнее OR. Получается (is_public = 1 AND title = '') OR 1=1. Правая часть истинна для каждой строки. Два дефиса -- начинают комментарий до конца строки; при показанном вводе добавленная обработчиком завершающая кавычка и ORDER BY оказываются в комментарии.
Это SQL-инъекция: недоверенный ввод изменил структуру SQL-команды. При параметризации структура задаётся заранее, а весь введённый текст передаётся как одно значение. Кавычки и SQL-слова внутри него не становятся новым условием.

        
Почему одной параметризации недостаточно для всего сервиса?
Она защищает передачу значений в этот SQL-запрос от изменения его структуры. Но если разработчик вообще уберёт is_public = 1, параметр не восстановит потерянное правило доступа. Права пользователя и допустимое состояние данных проверяются отдельно.
Параметр обозначает значение, а не произвольное имя таблицы, столбца или направление сортировки. Для таких частей запроса приложение выбирает из явно разрешённых вариантов. Проверка размера и смысла ввода тоже остаётся нужна.
HTTPS защищает транспортное соединение. После расшифрования сервер всё равно должен безопасно обработать полученный текст: шифрование не исправляет склейку SQL.

        
Что здесь действительно выполняется, а что является моделью?
Запрос выполняет SQLite из локальной библиотеки sql.js 1.13.0, а не PostgreSQL. HTTP и C++ показаны для объяснения: браузер не запускает C++-обработчик и не отправляет запрос серверу.
Версия движка появится после первого выполнения.
Каждый запуск получает новую базу в памяти отдельного Web Worker (фонового исполнителя JavaScript). После запуска он завершается. В этой демонстрации разрешён один подготовленный запрос, база переводится в режим чтения; длина ввода и число показываемых строк ограничены. Долгое выполнение прерывается по времени. Это не доказательство жёсткого ограничения памяти и не универсальная песочница для произвольного недоверенного кода.
Диагностика SQLite видна здесь для обучения. Реальный публичный API не должен выдавать клиенту внутренний SQL, полный текст ошибок и скрытые записи.

        
Проверить себя: что именно мы исправили?
Почему запрет кавычек остановил показанный ввод, но не выполнил требования поиска? Что произойдёт с тем же вводом при передаче параметром? Вернёт ли параметризация правило публикации, если его удалили из SQL?
Показать разбор ответа
Запрет остановил запрос с кавычкой ещё до SQLite, но отверг и допустимое название O'Reilly. Параметризация передаст весь текст как одно значение: совпадающего опубликованного названия для показанного изменяющего условие ввода нет, поэтому ожидаем пустой ответ. Если убрать проверку публикации из SQL, параметризация её не добавит. Надёжность передачи значения и правило доступа — разные обязанности.

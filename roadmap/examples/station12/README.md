# Redis: изолированная лаборатория станции 12

Здесь два разных опыта. `cache_model.cpp` воспроизводит выбранный порядок
событий без сети: показывает, почему TTL не мешает позднему читателю вернуть
старую копию. `cache_client.cpp` работает с настоящим Redis через hiredis:
различает отсутствие ключа, значение и ошибку, передаёт строку с нулевым байтом.
Модель не подменяет Redis, а Redis не подменяет основную базу приложения.

Для чтения главы ничего устанавливать не нужно. Для первого запуска нужны
C++20-компилятор и CMake 3.28+. Для сетевого опыта дополнительно нужны Docker
Engine с Compose v2, доступ к собственному учебному Docker и интернет для
получения образов/зависимостей. Если Docker недоступен, не запускайте его через
sudo и не меняйте права сокета ради этой лаборатории: достаточно офлайн-опыта.

## 1. Сначала модель без Redis

Из корня скачанного репозитория:

```sh
cd roadmap/examples/station12
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --target cache_model
ctest --test-dir build --output-on-failure
./build/cache_model
```

Вывод модели:

```text
TTL-only: 100, origin: 120
old fill accepted: false
reloaded: 120
at expiry: false
```

Первый читатель получил цену 100 до записи цены 120 и заполнил кэш только
после удаления ключа. В момент 40 мс TTL ещё не истёк, но цена уже старая.
Во второй ветке модель хранит нижнюю допустимую версию даже после удаления
значения. Проверка этой границы и заполнение выполняются неделимо **в модели**.
Программа не реализует общую транзакцию PostgreSQL+Redis и не защищает от
сбоя между COMMIT и доставкой новой границы версии.

## 2. Подготовьте отдельный Redis

Все следующие команды выполняются из той же папки `station12`.

```sh
python3 lab.py init
python3 lab.py compose config
python3 lab.py compose up
python3 lab.py compose ps
python3 lab.py check
```

`init` создаёт новый идентификатор проекта, пароль в `.env` и ACL-файл в
`runtime/`. Файл `runtime/owner.json` связывает параметры с этой папкой;
старые файлы не перезаписываются. Пароль не выводится на экран.
Порт хоста — **127.0.0.1:16379**, а внутри Docker-сети сервис называется
`redis` и слушает 6379. Для другого свободного порта заранее выберите
`python3 lab.py init --port 16380`. При конфликте порта не останавливайте чужие
контейнеры или чужой Redis.

Используйте именно `lab.py compose`, а не прямой `docker compose`.
В обычном Compose экспортированные переменные shell имеют приоритет даже
над `--env-file`; старый `COURSE12_PROJECT` мог бы выбрать другой проект.
Оболочка читает проверенный файл, явно задаёт `-f` и `-p`, удаляет внешние
управляющие `DOCKER_*`/`COMPOSE_*` и подставляет параметры своего опыта
поверх окружения. Никакой `.env` не исполняется как скрипт.

Перед запуском, перезапуском и завершением оболочка проверяет локальный
Docker context с Unix socket и метки принадлежности контейнеров, сети и
тома. При совпадении имени с чужими ресурсами она отказывает, а не принимает
их в управление. TCP/SSH-контексты и Windows named pipes этим вариантом
не поддерживаются; на Windows нужен соответствующий локальный WSL-стенд.
Глобальный context не переключается. Проверки не являются защитой от другого
администратора Docker, одновременно меняющего те же ресурсы.

`check`, `inspect` и запуск клиента на хосте сначала сверяют контейнер,
точный loopback-порт, образ и том, а уже затем подключаются к Redis.
Поэтому случайный сервер с похожей версией на другом порту не считается
принадлежащим лаборатории. Для этих команд тоже нужен доступ к своему Docker.
Старое состояние без `owner.json` не «исправляется» автоматически: для нового
опыта скачайте чистые файлы в другую папку; прежние данные не удаляйте.

Образ закреплён на `redis:8.2.11-alpine`; существование тега проверено по
официальному списку Docker Official Images 30.10.2026. Это конкретный учебный
стенд, не рекомендация бессрочно держать такую версию в production. Образы
с точным тегом могут обновляться: для побитовой фиксации нужна дополнительно
проверенная привязка по digest.

В `redis.conf` намеренно включены AOF с `appendfsync everysec`, периодический
RDB и `noeviction`. Предел `maxmemory 64mb` не равен всему RSS; контейнеру
дано 192 MiB. Это небольшой учебный запас, не универсальная формула размера.
При OOM или ошибке записи сохраните диагностику и остановите опыт.

ACL разрешает ограниченный набор команд и ключи только своего
`course12:<идентификатор>:`. Команды очистки всей базы, смены конфигурации
и управления другими пользователями не разрешены. В ACL лежит SHA-256
высокоэнтропийного пароля, а не пароль открытым текстом. `.env` и `runtime/`
не добавляйте в Git и не отправляйте другим людям.

Что именно проверяет `check`:

1. Подключение и версию сервера.
2. Различие `nil`, существующей пустой строки и двоичной строки `A\0B`.
3. Положительный PTTL и удаление по явно установленному нулевому сроку.
4. Ошибку одной команды EXEC без отката другой команды.
5. Конфликт WATCH через два независимых соединения.
6. Три разрешённых обращения и отказ четвёртому в учебном окне лимитера.
7. Отказ старому владельцу в удалении новой аренды.

Проверка пишет только ключи своего опыта. Не использует FLUSHDB/FLUSHALL,
не меняет конфигурацию сервера и не управляет Docker. При сетевой ошибке
она не повторяет автоматически команды с неизвестным результатом.

## 3. Настоящий C++-клиент

Для запуска полностью внутри учебного Docker-проекта:

```sh
python3 lab.py compose client
```

Контейнер клиента подключается к `redis:6379` в своей Compose-сети.
Контейнерная сборка использует `gcc:14.4.0-trixie` и hiredis `v1.3.0`.
Это большой **образ разработки** с инструментами, не минимальный production
runtime. Получение зависимостей требует сети; сборка не устанавливает их на хост.

Ожидаемый вывод после успешного обмена:

```text
first: miss
second: hit, bytes=3
after invalidation: miss
```

Либо соберите клиент на хосте (CMake скачает hiredis только в build-папку):

```sh
cmake -S . -B build -DCOURSE12_WITH_HIREDIS=ON
cmake --build build --target cache_client
python3 lab.py client
```

Helper читает свой `.env` как данные, передаёт клиенту loopback-адрес и пароль
через окружение. Не выполняйте `source .env`: это не скрипт. Клиент имеет
тайм-ауты, но они не превращают несколько сетевых команд в общий deadline.
Один `redisContext` принадлежит одному исполнителю; совместное использование
без внешнего протокола здесь не реализовано.

## 4. Перезапуск и граница вывода

`check` в конце оставляет отдельную метку без TTL. Сначала убедитесь,
что она есть, затем штатно перезапустите только Redis этого проекта:

```sh
python3 lab.py inspect
python3 lab.py compose restart
python3 lab.py compose up
python3 lab.py compose ps
python3 lab.py inspect
```

При запуске сервера дождитесь состояния healthy. Присутствие метки после
обычного перезапуска с сохранённым томом — результат именно этого опыта.
Это **не** проверка отключения питания, повреждения носителя, переключения
на реплику или обещания никогда не терять подтверждённые записи. Не пытайтесь
ломать рабочую машину для проверки AOF.

## 5. Завершение

```sh
python3 lab.py compose down
```

Оболочка явно выбирает проверенный уникальный проект из `.env`: останавливает его
контейнеры и убирает его сеть. Именованный том с данными сохраняется.
Не добавляйте `-v`, `--remove-orphans`, `docker system prune` и массовые
команды удаления. Если решили больше не хранить учебные данные, сначала
вручную установите точное имя принадлежащего проекту тома и убедитесь, что
он не нужен; автоматической команды удаления в этом практикуме нет.

В отчёте укажите версии, режим запуска, фактический вывод, обнаруженные ошибки
и что не проверялось. Отдельно объясните, почему успешные команды Redis не
доказывают свежесть основной БД, общую транзакцию или безопасную повторную
обработку любого внешнего эффекта.


Выбор C++20 или C++23 для локальной CMake-сборки
------------------------------------------------
По умолчанию проект остаётся на C++20. Для сравнения режимов используйте
разные каталоги сборки; команды выполняются в каталоге этого проекта:

    cmake -S . -B build-cxx20 -DCOURSE_CXX_STANDARD=20
    cmake --build build-cxx20
    cmake -S . -B build-cxx23 -DCOURSE_CXX_STANDARD=23
    cmake --build build-cxx23

COURSE_CXX_STANDARD допускает только 20 или 23. CMake требует выбранный
стандарт без перехода на более ранний и отключает расширения языка. Уже
существующие build-каталоги, настройки lab.py и контейнерные образы команды
выше не меняют. В каждый новый каталог отдельно передавайте нужные флаги
необязательных адаптеров из инструкции выше и установите указанные зависимости.

Для отдельного компилятора добавьте при ПЕРВОЙ настройке нового build-каталога:

    -DCMAKE_CXX_COMPILER=/absolute/path/to/g++

Не подменяйте компилятор в старом CMake cache. Сам режим -std=c++23 не обновляет
стандартную библиотеку и не доказывает поддержку всех возможностей C++23.
Текущие базовые исходники сохраняют требования C++20; поддержку нужных функций
и совместимость зависимостей проверяют для конкретной сборки. Это не перевод
Docker-образов или внешних SDK на другую версию.

После сборки проверьте зарегистрированные тесты отдельно в каждом режиме:

    ctest --test-dir build-cxx20 --output-on-failure
    ctest --test-dir build-cxx23 --output-on-failure

Основание выбора режима CMake 3.24:
https://cmake.org/cmake/help/v3.24/prop_tgt/CXX_STANDARD.html
https://cmake.org/cmake/help/v3.24/prop_tgt/CXX_STANDARD_REQUIRED.html
https://cmake.org/cmake/help/v3.24/variable/CMAKE_CXX_COMPILER.html

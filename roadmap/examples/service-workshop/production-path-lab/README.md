# Список дел: от входа пользователя до обработанного события

Анна и Борис ведут каждый свой список дел. После добавления дела оно сразу
появляется в списке, а отдельный обработчик увеличивает счётчик созданных дел.
Счётчик — простая замена фонового отчёта: он помогает заметить как потерянное
событие, так и повторное применение одного события. Существующее дело можно
переименовать, но это не новое создание и счётчик от переименования не растёт.

Здесь настоящие C++ HTTP API, PostgreSQL, AMQP-отправитель, RabbitMQ и отдельный
получатель. Мы намеренно завершаем процессы в неудобные моменты, затем проверяем
не сообщение «успех», а строки в базе и доступ другого пользователя.

## Граница опыта — прочитай до запуска

- Это **новый самостоятельный локальный стенд**, не обновление основного Task API.
  Нужна полная копия репозитория. Старый архив `lab.py pack` его не содержит.
- Linux/WSL, Python 3, локальный Docker Engine и Compose v2. Для сборки нужны
  интернет, место под образы и несколько минут; одновременно собираются два
  задания. Внутри стенда три постоянных сервиса и короткие одноразовые процессы.
- Единственный опубликованный порт привязан к `127.0.0.1`. PostgreSQL и RabbitMQ
  портов на хосте не публикуют; они находятся во внутренней сети. API дополнительно
  подключён к отдельной bridge-сети для опубликованного loopback-порта. Это не
  механизм запрета исходящих соединений API. У процессов есть пределы
  CPU, памяти и числа процессов. Это не разрешение работать с чужими серверами.
- HTTP и AMQP здесь **без TLS**. Нет защиты входа от перебора паролей, MFA,
  восстановления доступа, cookie-интерфейса браузера или промышленного управления
  секретами. Не подставляй настоящие пароли и не публикуй стенд на VPS.
- Один PostgreSQL и один RabbitMQ. Quorum queue состоит из одного участника:
  проверяем сохранение при перезапуске, **не высокую доступность** или потерю диска.
- API, relay и consumer используют разные SQL-роли, но одну PostgreSQL-инсталляцию.
  Это не три независимые базы и не распределённая транзакция между ними.

## Подготовка

Из корня локальной копии репозитория:

```sh
cd roadmap/examples/service-workshop/production-path-lab &&
python3 lab.py init --port 8089 &&
python3 lab.py check &&
python3 lab.py build &&
python3 lab.py up
```

Если порт занят, выбери другой **до** `init`. Инициализация создаёт случайное
имя `course-path-…`, идентификатор лаборатории и разные случайные пароли. Второй
`init` ничего не перезаписывает. Helper обращается только к локальному Docker
socket; удалённые context и переопределения Docker endpoint отвергаются.

`up` ждёт настоящего сервера PostgreSQL, запускает RabbitMQ, создаёт пользователей
`alice` и `bo` библиотекой libsodium и запускает API. Повторное заполнение не меняет
уже существующие пароли. Образы PostgreSQL и RabbitMQ могут потребовать загрузки.
RabbitMQ 4.4.0 закреплён digest, PostgreSQL использует обновляемый тег 18-bookworm;
фактическую версию нужно записывать в свидетельство своего запуска.

Секреты находятся в `.state/`. Каталог имеет режим `0700`, настройки — `0600`.
Файлы для контейнеров имеют `0444` **внутри закрытого каталога**: файловые secrets
в обычном Compose реализуются bind mount и не переназначают UID. Каждый сервис
получает только перечисленные ему файлы. Не меняй каталог на `0755`, не выводи
файлы, полный config/environment или токены в чат. Root и владелец Docker могут
прочитать эти секреты; этот стенд не защищает от администратора своего хоста.

## Обычная работа двух пользователей

```sh
python3 lab.py login --user alice &&
python3 lab.py login --user bo &&
python3 lab.py create --user alice --key create-a --title 'Prepare report' &&
python3 lab.py tasks --user alice &&
python3 lab.py tasks --user bo &&
python3 lab.py total --user alice &&
python3 lab.py inspect
```

В новом стенде у Alice одна задача с `version: 1`, у Bo пустой список. Общий
`inspect` показывает `tasks=1`, `outbox_pending=1`, `receipts=0`; счётчик Alice
пока `0`. Ответ создания означает фиксацию задачи и обязанности отправить событие,
а не завершение фоновой работы. Имена учебных аккаунтов английские; это не реальные
учётные записи и не предлагаемые пароли.

Вход возвращает bearer token (секрет, владения которым достаточно для обращения
к API). Helper сохраняет его в своём файле `0600`, но не печатает. Запросы передают
его только в `Authorization`, никогда в URL. В таблице сессий хранится BLAKE2b-хеш
случайного 256-битного токена, а не сам токен. Пароли проверяются другим механизмом:
`crypto_pwhash_str`/`crypto_pwhash_str_verify` libsodium с Argon2id и параметрами,
сохранёнными в строке проверочного значения. Быстрый хеш случайного токена не
следует переносить на пользовательский пароль.

Создание принимает только `title`. Номер владельца API получает из проверенной
сессии; поле `owner_id` в теле отвергается. Чтение и запись задачи включают владельца
в SQL-условие. Поэтому чужой известный ID не становится разрешением. API возвращает
одинаковый `404` для отсутствующей и чужой задачи, не раскрывая её содержимое.

## Повтор команды и один факт создания

Повтори точную команду создания с прежним ключом: получишь прежние ID/title/version,
без новой задачи и нового outbox. С прежним ключом и другим title будет `409`.
Этот ключ ограничен пользователем: Bo вправе использовать такую же строку для
собственной другой команды. Ключ — не пароль и не идентификатор пользователя.

Для переименования передай **фактические** ID и version из собственного вывода:

```sh
python3 lab.py rename --user alice --id 1 --version 1 --title 'Report renamed' &&
python3 lab.py create --user alice --key create-a --title 'Prepare report' &&
python3 lab.py tasks --user alice
```

В новой базе получится текущая задача `Report renamed`, version 2. Повтор POST
вернёт исходный ответ создания с version 1; это **не откат** текущей задачи.
Контракт сохраняет результат именно команды создания. Не копируй ID 1 вслепую
после предыдущих опытов. Неверная собственная version даёт `409`, чужая задача —
`404`, без изменения её названия.

```sh
python3 lab.py relay &&
python3 lab.py consume &&
python3 lab.py total --user alice &&
python3 lab.py inspect
```

Relay (исполнитель отправки) выбирает одну неотправленную запись с блокировкой
`FOR UPDATE SKIP LOCKED`, отправляет persistent-сообщение с прежним `event_id`,
ждёт publisher confirm и затем записывает `sent_at`. `mandatory` не позволяет
объявить обычным успехом возврат немаршрутизированного сообщения. Положительный
confirm ещё не означает, что consumer выполнил работу.

Consumer (получатель) одной SQL-транзакцией вставляет receipt — запись об уже
применённом событии — и увеличивает счётчик, **только если receipt действительно
добавлен**. Затем COMMIT и лишь после него manual ack брокеру. Повтор встречает
уникальный `(consumer,event_id)` и не увеличивает счётчик. Это одна защищённая
SQL-операция, не «ровно одна доставка» и не защита произвольного внешнего платежа.

Одноразовые команды обрабатывают максимум одну запись/доставку и завершаются.
Это сделано для наблюдения границ. Автоматического фонового retry, расписания,
контроля возраста outbox или промышленного graceful shutdown здесь нет.
Несколько relay могут пропускать занятые строки, поэтому общий порядок событий
не гарантируется. Счётчик создания допускает такой порядок: сложение коммутативно.

## Три настоящих падения процессов

Запускай эксперименты последовательно. Ненулевой код у намеренного падения —
ожидаемый результат: **не соединяй его со следующим шагом через `&&`**.

### 1. Задача записалась, HTTP-ответ не пришёл

```sh
python3 lab.py api-crash
```

Затем отдельно:

```sh
python3 lab.py create --user alice --key after-commit --title 'Commit before crash'
```

API выполняет COMMIT и выходит с кодом 86 до отправки ответа. Helper сообщит ошибку
соединения: это неизвестный клиенту результат, не доказательство rollback.

```sh
python3 lab.py api-normal &&
python3 lab.py create --user alice --key after-commit --title 'Commit before crash' &&
python3 lab.py inspect
```

Повтор находит прежнюю команду. На новом стенде после предыдущего примера задач две,
а не три. `api-crash` — явный локальный режим процесса, не доступный HTTP-заголовок.

### 2. Broker подтвердил, отправитель не записал sent_at

```sh
python3 lab.py relay --fault
```

Процесс выходит с кодом 87. Затем:

```sh
python3 lab.py inspect &&
python3 lab.py relay &&
python3 lab.py consume &&
python3 lab.py consume &&
python3 lab.py total --user alice
```

После падения обязанность остаётся pending. Повтор relay публикует **то же** событие.
Два consumer запуска видят одну новую обработку и один `duplicate`; счётчик увеличится
лишь на один. Дубликат здесь возник от двух публикаций, поэтому `redelivered` у него
не обязан быть `true`: это флаг повторной выдачи конкретной доставки, а не сравнение
бизнес-идентификаторов.

### 3. Эффект записан, ack ещё не отправлен

```sh
python3 lab.py create --user alice --key after-effect --title 'Effect before ack' &&
python3 lab.py relay
```

Затем отдельно:

```sh
python3 lab.py consume --fault
```

Код 88 означает завершение после SQL COMMIT, до ack. Следующий обычный `consume`
получает повторную выдачу, находит прежний receipt и не повторяет прибавление.
Сравни `inspect` и `total` до и после. Не заменяй receipt отметкой в памяти процесса:
именно память при таком завершении исчезла.

## Сессия должна прекращать доступ на сервере

```sh
python3 lab.py logout --user alice
python3 lab.py tasks --user alice
```

Вторая команда использует ещё сохранённый локальный токен, но получает `401`:
logout записал отзыв на сервере. Новый `login` выдаёт новый токен. В этом небольшом
контракте у пользователя только одна активная сессия, поэтому новый вход также
заменяет прежнюю. Это политика опыта, не универсальное правило любого сайта.

Сроки: 20 минут от входа и 5 минут с проверки сессии последней успешно
зафиксированной защищённой операции. Отметка берётся при проверке, а не
в момент отправки HTTP-ответа; откатившийся запрос её не сохраняет.
Чтобы не ждать, есть **административные учебные инъекции**: они меняют только
временные поля сессии выбранного учебного пользователя, не часы компьютера.

```sh
python3 lab.py login --user alice &&
python3 lab.py expire-idle --user alice
```

Отдельный `tasks --user alice` должен дать `401`. Повтори с `login`, затем
`expire-absolute`. Ошибка сети не равна истёкшей сессии: сравни HTTP-статус.
Проверка сессии берёт её строку `FOR UPDATE` и удерживает до конца защищённой
операции. Logout конкурирует за ту же строку. Уже начавшееся действие автоматически
не отменяется; успешный отзыв определяет границу для следующих действий.

## Автоматическая приёмка на новом стенде

```sh
python3 test_lab.py &&
python3 acceptance.py --run-local-docker --report /tmp/course-path-my-acceptance.json
```

Приёмка копирует публичные исходники во вновь созданный временный каталог,
создаёт **другой** случайный проект и свободный loopback-порт. Она не использует
текущие задачи. Сборка выполняется из этих исходников; `--image` нужен только
разработчику для явно записанного повторного использования локального образа.
Проверяются обычная работа, все три падения, потерянный HTTP-ответ, несовпадение
payload, два пользователя, чужая запись, повторный вход, logout, оба срока,
перезапуски БД/брокера, недоступность брокера и БД, запрет SQL-роли и отсутствие
сгенерированных секретов в собранных журналах. Это ограниченный набор негативных
проверок, не аудит безопасности или доказательство всех конкурентных расписаний.

В `finally` приёмка проверяет метки владения и удаляет только ресурсы своего
проекта, включая его два учебных volume. Отчёт получает режим `0600`; он не
содержит паролей или токенов. Существующий файл отчёта не перезаписывается.

## Остановка и данные

```sh
python3 lab.py down
```

Контейнеры и сеть остановятся; данные остаются в двух именованных volume.
`up` вернёт прежний стенд. Если намеренно нужен **необратимый** сброс только этих
учебных данных:

```sh
python3 lab.py down --delete-data
```

Helper проверяет случайное имя и метки контейнеров/volume/сети; глобальных `prune`
или удаления директорий нет. Приватные настройки сохраняются; после удаления
volume следующий `up` создаст новую пустую базу с теми же учебными аккаунтами.
Старые сохранённые токены уже не действуют — выполни `login`. Docker-образы остаются
как кэш; helper не удаляет чужие образы и не меняет настройки хоста.

## Почему это ещё не production

Проверенный путь имеет вполне конкретные границы: запись одной команды, доставка
одного вида события, защищённое прибавление и простой владелец задачи. Очередь
ограничена `x-max-length=1000` с `reject-publish`, но quorum queue может немного
превысить предел из-за публикаций в полёте. После пяти учитываемых неудачных выдач
сообщение уходит через DLX; это не бесконечный автоматический retry. В 4.4 лимит
считает реальные неудачи выдачи, включая потерю соединения, не каждый `basic.nack`.
DLX по умолчанию не даёт гарантии сохранения при недоступной целевой очереди.
Фиксированные queue arguments удобны в новом закрытом стенде; для работающей
топологии меняемые оператором политики обычно предпочтительнее.

Нужны отдельные решения для TLS, ротации секретов, разрешений брокера по ролям,
наблюдения и оповещений, backlog, retention receipt/outbox/commands, восстановления
после потери диска, шардирования, независимых БД и непрерывного запуска workers.
Удалив receipt раньше возможного повтора, можно снова применить старое событие.
Скомпрометированный доверенный publisher может прислать ложное событие; здесь
используется один учебный broker account, не полная схема изоляции всех сервисов.

## Источники контракта

### Дополнительная практика PostgreSQL: отстающая копия и новая роль

Программа со списком дел может читать с копии базы, но сразу после сохранения
новое дело там ещё не видно. Отдельный опыт позволяет самому увидеть разницу между
приёмом журнала и его применением. Затем проверим, почему ожившую прежнюю основную
базу нельзя просто вернуть клиентам, и создадим новую копию актуальной истории.
Это не использует данные API, его брокер или их volumes.

Нужен уже имеющийся локальный официальный образ `postgres:18-bookworm`.
Из того же каталога:

```sh
python3 replication_lab.py --run-local-docker --interactive \
  --report /tmp/course-pg-recovery-my-run.json
```

Файл отчёта должен быть новым, его родительский каталог — существующим. Скрипт
проверяет локальный Docker endpoint и создаёт отдельные случайные имена. Ни один
порт не публикуется. Все базы находятся в своей внутренней сети; CPU, RAM и число
процессов ограничены. Секреты создаются в приватном временном каталоге, не выводятся.
Копия получает пароль репликационной роли через passfile: в volume он устанавливается
с владельцем PostgreSQL и режимом `0600`. Доступ администратора по Unix socket
внутри этих контейнеров доверенный; это не настройка публичного PostgreSQL.

С `--interactive` Enter продолжает следующий этап, Ctrl-C очищает только этот опыт.
Без этого флага сценарий выполняет те же проверки подряд. На экране появляются
фактические состояния, а не заготовленный вывод:

| Этап | Проверяемое состояние |
| --- | --- |
| Primary создала задачу | 1 строка |
| `pg_basebackup -R -X stream` развернул standby | 1 строка; `pg_is_in_recovery()=true`; INSERT отклонён |
| Запросили pause, дождались состояния `paused`, сделали COMMIT на primary | У primary 2 строки, у standby 1 |
| Получение догнало целевой flush LSN при остановленном replay | WAL получен и синхронизирован, новая строка всё ещё не видна |
| Resume и ожидание применения | У standby 2 строки и достигнута нужная replay-позиция |
| Старую primary остановили и отключили от сети, затем `pg_promote` | Новая primary writable; записана третья строка |
| Старую БД запустили только в изоляции | Она всё ещё не в recovery, содержит 2 строки вместо новых 3 |
| Её снова остановили; новый base backup от promoted primary в пустой другой volume | Новая standby видит 3 строки |
| Primary записала четвёртую строку | Новая standby получает её потоковой репликацией |

LSN — позиция записи в WAL, журнале восстановления. В отчёте сохраняются конкретные
receive/replay-позиции этого запуска. Число байтов между ними нельзя без нагрузки
и скорости превратить в универсальные секунды задержки. Пауза replay введена
намеренно; сеть и WAL receiver при этом продолжают работать. Проверяется достигнутое
`pg_get_wal_replay_pause_state()='paused'`, поскольку один запрос pause ещё не
означает, что применение уже остановилось.

Перед promotion выполняется ручное fencing: подтверждённая остановка процесса
и отключение прежнего primary от единственной сети опыта. Это не автоматические
выборы лидера и не проверка независимых машин. При возвращении старый контейнер
остаётся без сетевых endpoints и host-портов; к нему не направляются прикладные
записи. Важное наблюдение — он сам не превратился в standby. Новую копию создают
из выбранной актуальной истории, а не переименовывают старые файлы.

`pg_basebackup` копирует весь небольшой кластер, не отдельную таблицу. Старый
volume остаётся отключённым до очистки; свежая копия создаётся в другом пустом
volume. Это реальное физическое восстановление новой standby, но **не** выполненный
`pg_rewind` и не PITR (восстановление на выбранный момент по архиву WAL).
Replication slot помогает удерживать журнал для копии; это потребляет место и
нуждается в контроле. В опыте установлен предел удержания, малая нагрузка и
конечные ожидания, а не обещана бесконечная сохранность отставшего узла.

На каждом выходе скрипт проверяет метки и удаляет только свои контейнеры, три
volume и сеть. Эти временные данные удаляются **необратимо**, отчёт остаётся.
При аварии самого Docker/хоста очистка может не завершиться: отчёт отмечает это,
а не скрывает проблему. Глобальных `prune`, чужих баз и удаления директорий нет.

Здесь заранее дождались заданной строки и только потом переключили роль. Это
подтверждает конкретную последовательность, но не нулевой RPO при произвольной
аварии асинхронной репликации. Не измерены RTO под нагрузкой, потеря диска,
автоматическое failover/fencing и переподключение API. Реплика не заменяет
независимую резервную копию: ошибочное удаление воспроизводится и на ней.

# Совместимый выпуск: две C++-версии и одна схема PostgreSQL

Это отдельная лаборатория после Task API: два настоящих исполняемых C++20-файла
работают с одной учебной базой. V1 знает `id/title/version`; V2 дополнительно
читает и изменяет `note`. Проверяем добавление поля, смешанное использование,
возврат к V1 и повторный переход на V2 **без потери уже записанного note**.

Здесь нет HTTP-сервера, переключения прокси или rolling deployment. «Вернуть
V1» означает снова выбирать старый исполняемый файл для операций. Настоящие
HTTP-запросы и нагрузка — основной серверный практикум; этот небольшой опыт
изолирует совместимость бинарников и данных, чтобы причина результата была ясна.
В нём одна фиксированная задача `id=1`, а не второй полноценный Task API.

## Подготовка

Нужны Linux/WSL, Python 3 и уже настроенные Docker Engine/Compose v2. Работайте
из **полной локальной копии репозитория**, в этом каталоге:

```sh
cd roadmap/examples/service-workshop/release-lab &&
python3 release_lab.py init &&
unset RELEASE_LAB_PROJECT POSTGRES_PASSWORD APP_DB_PASSWORD &&
python3 release_lab.py check-env &&
docker compose --profile tools config --quiet &&
docker compose up -d --wait --wait-timeout 120 db &&
docker compose build v1 v2
```

`cd` указан от корня репозитория. Init создаёт новый случайный project name и
два независимых пароля в `.env` с правами 0600; не заменяет существующий файл.
Экспортированные значения удаляются только из текущего shell, не из файла.
Не выводите `.env` или `docker compose config` без `--quiet` в чат/скриншоты.
Проверьте Docker context: это должен быть ваш учебный компьютер, не рабочий daemon.

Оба бинарника собираются из `client.cpp` с разным `RELEASE_VERSION`, используя
libpqxx 7.10.1 с закреплённым хешем архива. Первая сборка может потребовать
интернет для базового Debian-образа, пакетов и библиотеки. Теги базовых образов
не обещают побайтового повторения через месяц; для контролируемого релиза их
закрепляют реально проверенными digest и обновляют отдельно.

PostgreSQL 18 находится только во внутренней Docker-сети, порты не опубликованы.
Клиенты одноразовые, непривилегированные, с ограничениями CPU/RAM/PIDs. Они
получают роль `release_app`, не `postgres`. Docker/root всё равно может прочитать
environment-секреты. Это локальный стенд, не рецепт публичного развёртывания.

Архив `python3 ../lab.py pack` основного сервиса намеренно не включает этот
вложенный опыт. Перенос на VM для него не нужен; используйте полный репозиторий.

## 1. Старая схема и настоящая запись V1

```sh
docker compose run --rm --no-deps v1 show &&
docker compose run --rm --no-deps v1 rename 1 'Before expand'
```

После служебных сообщений Compose программа выводит:

```text
v1 id=1 title="Original" version=1
v1 id=1 title="Before expand" version=2
```

Число после `rename` — **ожидаемая версия**, а не ID. ID=1 фиксирован в этом
учебном клиенте. UPDATE меняет `title` и увеличивает `version`, только если
прочитанная версия ещё актуальна. Не подставляйте следующий номер механически,
если уже выполнили дополнительные записи: сначала вызовите `show`.

Начальную схему создаёт `001-initial.sql` только при пустом volume. Отдельная
роль `release_owner` владеет таблицами, но не может войти в базу (`NOLOGIN`).
Приложению даны только нужные права столбцов. Оно не может изменить таблицу
командой ALTER или стать владельцем. Администратор понадобится для миграции,
но эти полномочия не передаются каждому обычному запросу приложения.

## 2. Сначала expand, затем новая версия

```sh
docker compose exec -T db psql -X -U postgres -d release_course \
  -v ON_ERROR_STOP=1 --file /opt/release-lab/002-expand-note.sql &&
docker compose run --rm --no-deps v1 show &&
docker compose run --rm --no-deps v2 show
```

Ожидаем `version=2` в обеих программах, а V2 дополнительно показывает `note=NULL`.
Миграция добавила допускающий NULL столбец; старые строки не требуют выдуманной
заметки. NULL — отсутствие значения, не пустая строка. Существующий `title`
не переименован и не удалён. Поэтому SELECT V1 со списком известных столбцов
по-прежнему работает, а V2 уже может запросить note.

Миграция выполняет `SET LOCAL ROLE release_owner`, ALTER, выдачу прав на note
и запись версии схемы в одной транзакции. `lock_timeout=2000ms` ограничивает
ожидание блокировки, `statement_timeout=5000ms` — выполнение команды. Это не
обещание миграции без блокировок на любой таблице. При ошибке остановитесь,
исследуйте состояние; не повторяйте вслепую и не добавляйте DROP. Второй запуск
этого же шага намеренно завершается ошибкой, а не скрывает неизвестное состояние.

V2 до expand не работает: её SELECT требует note. Из этого опыта нельзя делать
вывод «любая новая версия совместима со старой схемой». Мы выбрали порядок:
совместимое расширение схемы → новая версия приложения.

## 3. Смешанное окно: старый writer не стирает новое поле

```sh
docker compose run --rm --no-deps v2 set-note 2 'Keep this note' &&
docker compose run --rm --no-deps v1 rename 3 'Edited by old version' &&
docker compose run --rm --no-deps v2 show
```

Итог: `title="Edited by old version" version=4 note="Keep this note"`.
Причина не в терпимости PostgreSQL к старым программам, а в конкретном SQL:

```sql
UPDATE release_lab.tasks
SET title=$1, version=version+1
WHERE id=1 AND version=$2 AND version<9223372036854775807
RETURNING id,title,version;
```

Это запрос V1. Он перечисляет изменяемые столбцы и не трогает note. Вариант
«собрать всю строку заново из старого объекта», подставляя NULL в неизвестные
поля, нарушил бы наш договор. Наличие добавочного столбца само по себе от этого
не защищает. Для HTTP API отдельно согласуют смысл PUT/PATCH и представлений;
наш CLI не выдаёт этот SQL за универсальную реализацию PUT.

Обе версии используют **один** счётчик version. Попытка V2 записать по уже
устаревшей версии 3 должна завершиться кодом 2 и строкой not_applied:

```sh
docker compose run --rm --no-deps v2 set-note 3 'Must not appear'
docker compose run --rm --no-deps v2 show
```

Это ожидаемый отказ, не сломанная сборка. Вторая команда по-прежнему показывает
version=4 и Keep this note. Не соединяйте эти команды через `&&`: первая
специально возвращает ненулевой статус, чтобы отказ нельзя было спутать с записью.

## 4. Возврат старого приложения не означает возврат старой схемы

Теперь считаем V2 отозванной и выполняем изменения только старым бинарником:

```sh
docker compose run --rm --no-deps v1 rename 4 'Rollback stays compatible' &&
docker compose exec -T db psql -X -U postgres -d release_course \
  -v ON_ERROR_STOP=1 -c 'SELECT id,title,version,note FROM release_lab.tasks;'
```

Получаем title=Rollback stays compatible, version=5, note=Keep this note.
Последнее проверяет администратор: V1 не показывает неизвестное ей поле.
Не выполняем обратный ALTER и не удаляем note. Иначе возврат одной программы
уничтожил бы данные, которые уже успела сохранить другая.

Повторно выбираем V2 и выполняем новую запись, а не просто меняем метку версии:

```sh
docker compose run --rm --no-deps v2 set-note 5 'Forward again' &&
docker compose run --rm --no-deps v2 show
```

Итог: `v2 id=1 title="Rollback stays compatible" version=6 note="Forward again"`.
История миграций всё ещё содержит 1 и 2. Возврат бинарника не отменил схему,
уже записанную заметку или промежуточные пользовательские изменения.

## 5. Почему contract отложен

Contract — удаление переходной совместимости после ухода старых пользователей
схемы и закрытия согласованного окна возврата. В этом опыте добавленное note
нужно V2, а title нужно обеим версиям: удалять нечего. Отсутствие команды DROP
не означает незавершённую миграцию. Если позже понадобится переименовать title,
потребуется отдельный переход с поддержкой обоих форматов и переносом данных.

Остановить именно эту лабораторию, сохранив данные:

```sh
python3 release_lab.py check-env &&
docker compose down
```

Именованный pgdata останется. Не добавляйте `-v`, если хотите сохранить опыт;
удаление единственного volume необратимо без копии. Повторный init не сбрасывает
проект. Для чистого опыта возьмите новую копию каталога без приватной `.env`,
создайте новое имя через init и не смешивайте результаты разных баз.

## Приёмка и границы

- После expand V1 читает старые поля, V2 видит NULL в новом.
- Запись note через V2 сохраняется после настоящей записи title через V1.
- Устаревшая expected_version не меняет данные.
- Возврат на V1 оставляет схему и note; следующий V2 использует их.
- Приложение не владелец таблиц и не выполняет DDL.
- Результат не доказывает HTTP drain, бесшовный rolling release, совместимость
  любого ORM, всех форматов сообщений или миграций большого production-хранилища.

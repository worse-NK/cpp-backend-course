# Локальный пример станции 9

Целевые версии: C++20, libpqxx **7.10.1**, PostgreSQL **18**; CMake >= 3.20,
pkg-config и установленная libpq/libpqxx с development-файлами.
API сверено с документацией libpqxx 7.10.1. Оба примера собраны GCC 13.3
с C++20 и libpqxx 7.10.1 и выполнены против PostgreSQL 18 (11 октября 2026).
Не использовать этот проект как готовый production-сервис.

## Подготовка

Нужен доступ к отдельному локальному PostgreSQL под непривилегированной учебной
ролью, которой разрешено создать свою базу. Не запускайте против рабочей базы.
Установку сервера и создание роли выполняют отдельно под свой дистрибутив.

1. Создайте пустую БД `cpp_course9` с владельцем — вашей учебной ролью:
   `createdb cpp_course9`. Команда использует параметры подключения libpq;
   при необходимости укажите `-h`, `-p`, `-U` явно.
2. `psql -X --set ON_ERROR_STOP=on --dbname=cpp_course9 --file=schema.sql`
3. `cmake -S . -B build` и `cmake --build build` из этой папки.
4. Укажите строку подключения без пароля в исходниках:
   `export CPP_COURSE_DB='dbname=cpp_course9 connect_timeout=5'`.
   Это пример для локальной настройки libpq; TCP-host/user задаются по вашей установке.
   Если нужен пароль, используйте защищённый password file libpq, не Git.
5. `./build/task_edit 'Проверить API'`.

На исходных данных ожидается `10 | Проверить API | 2`, код выхода 0.
Повтор с тем же ожидаемым номером версии (он намеренно равен 1 в коде)
даёт `not_applied: absent, inaccessible, or stale version`, код 2.
Это не автоматический повтор: сначала следует решить конфликт.
Проверить состояние: `SELECT id, title, version FROM tasks WHERE id = 10;`.

Проверьте также кавычку в заголовке (`O'Reilly`) и текст, похожий на SQL.
В свежем сценарии это данные параметра, а не новая SQL-команда. Пример не
реализует HTTP, аутентификацию, пул, журнал событий или автоматические повторы.
`actor_id=1` здесь учебный вход; в сервисе он должен поступать из проверенной сессии.

Ни скрипт, ни приложение не удаляют существующие базы/таблицы. Для новых сценариев
предпочитайте новую изолированную базу с другим именем и соответствующей строкой
подключения; не запускайте повторно создание схемы поверх чужих данных.

## Разбор последнего места

`parking.cpp` — самостоятельная полная программа, CMake-цель `reserve_slot`.
Сначала в учебной базе выполните `psql -X -v ON_ERROR_STOP=1 -d cpp_course9 -f parking.sql`.
Затем с той же переменной `CPP_COURSE_DB` запустите `./build/reserve_slot`.
Ожидается `reserved; remaining=0`, код 0. Повторный запуск:
`not_reserved: full or absent`, код 2. Это одна попытка захвата, а не готовый
HTTP endpoint: журнал бронирований, проверка пользователя и идемпотентность
запросов сюда намеренно не включены. Счётчик нельзя повторно уменьшать вслепую
после неизвестного исхода COMMIT.

## Изолированный PostgreSQL для SQL-лабораторных

Из корня репозитория, при установленном Docker и Python 3:

```sh
docker run --detach --name cpp-course-station9-check-demo \
  --network none --tmpfs /var/lib/postgresql:rw \
  --env POSTGRES_HOST_AUTH_METHOD=trust postgres:18
python3 roadmap/examples/station9/verify.py cpp-course-station9-check-demo
```

У контейнера **нет сети и опубликованных портов**. Режим trust допустим здесь
только для одноразового стенда: не используйте его у сервиса с сетевым доступом.
Данные находятся в памяти и исчезнут при остановке контейнера. Скрипт создаёт
свои `course9_verify` и `course9_restored`; повтор в той же базе намеренно
завершится ошибкой, а не уничтожит предыдущие данные.

Для ручной работы откройте два терминала с:
`docker exec -it cpp-course-station9-check-demo psql -X -U postgres -d course9_verify`.
В каждом вводите шаги A/B из итогового разбора. После автоматической проверки
мест уже нет: для нового опыта в этом стенде установите `available=1`.
Не путайте это с восстановлением реальной парковки: здесь только учебные данные.

По окончании удалите **только этот одноразовый стенд**:

```sh
docker rm -f cpp-course-station9-check-demo
```

Вместе с ним безвозвратно исчезнут учебные данные из памяти. Никакие базы на
хосте скрипт не изменяет. Для сохранения своих экспериментов сначала сделайте копию.

## Что проверяет verify.py

- LEFT JOIN, COUNT и фильтрацию NULL; ограничения FK, NOT NULL, CHECK.
- Откат изменения и пропуски sequence после отката.
- Последнее место: две реальные сессии, наблюдение ожидания Lock в
  `pg_stat_activity`, затем COMMIT или ROLLBACK первой сессии.
- Разные снимки Read Committed и Repeatable Read.
- Write skew при Repeatable Read и отказ Serializable с SQLSTATE 40001.
- Добавление столбца, заполнение, NOT NULL; pg_dump и восстановление
  в **другую пустую базу**, включая повторную проверку внешнего ключа.

Это не проверка производительности production-сервиса, отказоустойчивости диска,
репликации, PITR или всех вариантов сетевого сбоя COMMIT.

Для полного автоматического прогона C++ в Linux-контейнере можно собрать
отдельный проверочный образ (потребуются интернет и доверенные TLS-сертификаты):

```sh
docker build -f roadmap/examples/station9/Dockerfile.verify \
  -t cpp-course-station9-verify:local roadmap/examples/station9
docker run --detach --name cpp-course-station9-check-cpp \
  --network none --tmpfs /var/lib/postgresql:rw \
  --env POSTGRES_HOST_AUTH_METHOD=trust cpp-course-station9-verify:local
python3 roadmap/examples/station9/verify.py cpp-course-station9-check-cpp --cpp
```

Затем удалите только `cpp-course-station9-check-cpp` тем же способом.
В текущей среде загрузка Debian-пакетов внутри сборочного контейнера была
недоступна. Поэтому фактическая проверка выполнена иначе: libpqxx 7.10.1
собрана локально во временной папке, оба исполняемых файла собраны CMake
и скопированы в изолированный PostgreSQL-контейнер. Прошёл полный `--cpp`-прогон.
Установка зависимостей в систему пользователя не выполнялась.

## Проверка плана и самостоятельная работа

В разделе «Версии строк, уборка и измерение плана» есть TEMP-таблица на 100000
строк. Запустите обе команды EXPLAIN в одной сессии и сравните планы до/после
индекса. Результат выборки — 100 строк, но конкретный план и миллисекунды не
фиксированы. В разделе практики также есть самостоятельный отчёт LEFT JOIN
и задание на конкурентное место/восстановление.

ЛАБОРАТОРИЯ: НЕ ДАТЬ ОДНОМУ КЛИЕНТУ ЗАНЯТЬ СЕРВЕР НАВСЕГДА

Представь программу, в которую измерительные приборы присылают короткие
сообщения. Прибор отправляет длину и само сообщение, а сервер возвращает
те же байты. Этот простой ответ позволяет проверить обмен, не отвлекаясь
на обработку измерений. Но прибор может прислать только начало сообщения,
замолчать или перестать читать ответ. Сервер должен освободить занятые
ресурсы и продолжить обслуживать остальных.

Здесь настоящий C++-сервер, а не браузерная модель. Он слушает ТОЛЬКО
127.0.0.1. Ничего не открываем в интернете, не меняем firewall, настройки
ядра и службы ОС. Клиент verify.py соединяется только с процессом, который
сам только что запустил. Нельзя менять его цель на чужой сервер.

ФАЙЛЫ И ПРЕДПОСЫЛКИ

Сохрани server.cpp, CMakeLists.txt, verify.py и этот README вместе в новой
папке. Нужны Linux/POSIX, C++20 либо C++23, CMake >=3.22, Python >=3.10
и заголовки Boost 1.85.0. Boost в примере выбран по версии документации
основной главы, а не объявлен новейшей версией. Boost.System этой версии
используется в обычном header-only режиме; отдельная libboost_system
этому проекту не нужна. Зависимости глобально этот проект не устанавливает.

Если Boost отсутствует, официальный архив:
  https://archives.boost.io/release/1.85.0/source/boost_1_85_0.tar.bz2
Официальная метаинформация:
  https://archives.boost.io/release/1.85.0/source/boost_1_85_0.tar.bz2.json
Ожидаемый SHA-256:
  7009fe1faa1697476bdc7027703a2badb84e849b7b0baad5086b087b971f8617

Скачай архив в свою новую временную папку, проверь sha256sum и только при
совпадении распакуй. Понадобится заметное место: архив около 119 МиБ,
заголовки после распаковки больше. Не подставляй системную папку в качестве
места распаковки. Не выполняй bootstrap/b2/install: здесь нужны заголовки.
Boost_ROOT ниже должен указывать на папку с подпапкой boost/.

СБОРКА

Из папки лаборатории; путь к Boost замени своим настоящим путём:

  COURSE_ASIO_BUILD=$(mktemp -d -t course-asio-build.XXXXXX)
  cmake -S . -B "$COURSE_ASIO_BUILD" -DBoost_ROOT=/absolute/path/boost_1_85_0 -DCOURSE_CXX_STANDARD=20
  cmake --build "$COURSE_ASIO_BUILD" -j2
  ctest --test-dir "$COURSE_ASIO_BUILD" --output-on-failure

Для второй редакции создай ДРУГУЮ временную build-папку и выбери 23.
Компилятор задают при первой конфигурации через CMAKE_CXX_COMPILER.
Успешная сборка 20 не подтверждает, что какой-то другой проект поддерживает
все средства 23. В этом сервере используются общие для обеих редакций средства.

ВЫПОЛНЕНИЕ ПО ШАГАМ

1. Прочти договор сообщения, ещё не код.

Первые 4 байта — беззнаковая длина тела в сетевом порядке: старший байт
раньше младшего. Затем идут ровно столько байтов тела. Допустимо 1..65536.
Например, длина 5 и слово hello:
  00 00 00 05 68 65 6c 6c 6f

В Python запись struct.pack("!I",5) строит заголовок; ! задаёт сетевой
порядок, I — четырёхбайтовое беззнаковое число этого формата. На одну
TCP-связь принимаем только ОДНО сообщение и возвращаем один такой же кадр.
Кадром здесь называем прикладные длину+тело, не Ethernet-кадр.
Один send не обязан совпасть с одним recv или TCP-сегментом.

2. Проследи нормальную работу.

Server принимает связь и создаёт Session. Реестр сервера и активные
обработчики удерживают Session через shared_ptr. Сначала async_read
заполняет 4 байта header_. Длина проверяется ДО resize. Потом async_read
заполняет body_. Затем async_write отправляет header_ и body_ вместе.
Короткий массив buffers содержит только описания памяти; сами байты
остаются в полях Session до окончания операции.

Всё состояние меняет один поток io.run(). Это причина отсутствия mutex,
а не свойство shared_ptr. Просто добавить второй run-поток нельзя:
понадобится согласовать Session, реестр, таймеры и остановку.

3. Запусти проверку, затем открой verify.py.

  python3 verify.py "$COURSE_ASIO_BUILD/bounded_server"

Сначала проверяются нормальный обмен и отправка входа несколькими частями.
Получатель должен собрать тот же кадр. Затем длины 0,65537 и 4294967295
отклоняются до создания большого тела. EOF после части тела не считается
успешным коротким сообщением. Мы проверяем именно договор, а не надеемся,
что TCP соберёт предметное сообщение за программу.

4. Разбери медленного отправителя и медленного читателя отдельно.

У Session один deadline: принятие соединения +budget. Тот же срок охватывает
заголовок, тело И ответ. Клиент, приславший один байт, не получает новый
полный budget за каждый следующий байт. В тесте бюджет 600 мс — условие
опыта, не измеренная рекомендация для промышленного сервиса.

Для медленного читателя клиент задаёт маленький приёмный буфер, отправляет
полное большое сообщение и временно не читает ответ. У сервера маленький
send_buffer_size(4096), специально выбранный для этого опыта. Запись не
должна бесконечно удерживать Session. Требуем наблюдаемый исход
  finish deadline phase=write
а не делаем вывод о блокировке только по sleep клиента. Конкретные размеры
буферов ОС могут отличаться от запрошенных. Это не настройка производительности
для копирования в production.

Обратное давление (backpressure) здесь создаёт сам порядок: новая прикладная
работа не читается, пока идёт ответ. Очереди будущих ответов нет вообще.
Это особенно простой однокадровый протокол; HTTP/2 или многосообщенческий
протокол потребовал бы другого, явно ограниченного устройства очередей.

5. Проверь остановку под нагрузкой.

Вторая часть теста открывает 20 соединений при пределе 16 активных Session.
Лишнее соединение закрывается без создания Session; это отказ при входе,
а не гарантия успешного обслуживания каждого клиента. Затем тест посылает
SIGTERM ТОЛЬКО собственному дочернему серверу. Server закрывает acceptor,
даёт уже принятым запросам до 300 мс на завершение и закрывает оставшиеся
с исходом shutdown_limit. Все отменённые операции ещё получают завершения.
io.stop() не вызывается: завершениям нужно дать исполниться.

Строка stopped active=0 подтверждает пустой прикладной реестр после io.run().
Проверка также сравнивает accepted с finished, peak<=16, resident=0 и
peak_resident<=16. Реестр может
опустеть чуть раньше уничтожения последнего callback: его shared_ptr
по-прежнему удерживает Session. После выхода из run незавершённой работы
этого сценария не осталось. Это не обещание выхода строго через 300 мс:
планировщик ОС и занятый обработчик могут задержать выполнение таймера.

ЧТО ИМЕННО ОГРАНИЧЕНО

16 ЖИВЫХ Session ×65536 байтов тела =1048576 байтов полезных размеров тел максимум.
Число активных записей реестра и число живых Session — не одно и то же.
После finish отменённые callback ещё могут удерживать объект и его тело.
Поэтому отдельный ResidentCount освобождает место лишь в деструкторе Session,
а accept проверяет именно этот счётчик. Удаление из реестра само не открывает
место новой сессии. Счётчик удерживается shared_ptr и переживёт нужные объекты;
вся работа по-прежнему однопоточная. 80 быстрых отклонений при закрытии/приёме
дополнительно проверяют peak_resident, но сам предел задаёт это правило кода.
Это НЕ полный расход памяти процесса: есть ёмкость vector, управляющие
объекты, служебная память Asio, аллокатор и отдельные сетевые буферы ядра.
Ограничены число прикладных сессий, допустимая длина и логический срок,
но не доказана жёсткая верхняя граница RSS или реального времени.

done_ делает finish однократным. Проверка deadline в I/O-обработчике нужна,
потому что успешный таймер мог уже стоять в очереди. cancel не превращает
ранее готовый успех в operation_aborted. close отменяет ещё ожидающий I/O,
но не стирает уже готовое завершение. Поэтому поздний callback сначала
проверяет done_, а не начинает следующий шаг.

Завершение async_write означает завершение передачи через данный API,
не подтверждение, что другой прибор уже обработал измерение. TLS, вход
пользователя, надёжное хранение и повтор бизнес-операции здесь не реализованы.
При ошибке выделения памяти, инициирования операции или приёма процесс
заканчивается с fatal и ненулевым кодом. Это сознательный предел упражнения,
не сервер с восстановлением после всех ресурсных отказов. Он не production-ready.

УБОРКА

verify.py завершает только созданные им дочерние процессы. Проверь их
завершение. Временные build-папки и архив Boost принадлежат только этому
опыту; после проверки можешь удалить именно их через файловый менеджер.
Не удаляй общую установленную библиотеку и не используй широкий шаблон
для рекурсивного удаления. Сетевых настроек для восстановления здесь нет.
